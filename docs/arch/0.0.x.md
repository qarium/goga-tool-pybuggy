# Architecture Plan — pybuggy-config-init

> Интерактивное построение `.goga/tools/pybuggy/config.yml` командой `init`.

- **Topic:** `pybuggy-config-init`
- **Plan path:** `docs/arch/0.0.x.md` (имя по текущей ветке `0.0.x`)
- **Source task:** `docs/tasks/0.0.x.md`
- **Language:** Python (goga-cell-python)
- **Scope:** единая задача — расширение ячейки `commands/init` (интерактивный шаг построения `config.yml` + новые импорты + снятие ограничения) и сопутствующее раскрытие `PluginConfigKeys` контрактом ячейки `plugin`. Декомпозиция не требуется.

---

## Implementation Order

Порядок — от листьев к корню (ячейки без зависимостей первыми).

1. **`goga_tool_pybuggy/config`** — UNCHANGED provider.
   - Причина: не имеет Imports, от кого зависел бы для этой задачи; поставляет схему `SpecEntry`/`GitEntry` (+ `configuration` usage) для `init`. Код и контракт не меняются.

2. **`goga_tool_pybuggy/plugin`** — MODIFY contract (leaves).
   - Причина: зависит только от `api` и `plugin/loaders` (не от `init`/`config`); раскрывает `PluginConfigKeys` как импортируемый тип ДО того, как `init` будет его импортировать. Состав enum не меняется.

3. **`goga_tool_pybuggy/commands/init`** — MODIFY (root).
   - Причина: зависит от `config` (импорт `SpecEntry`/`GitEntry` + `configuration`) и `plugin` (импорт `PluginConfigKeys`); реализуется последним, когда зависимости готовы. Точка основного изменения: +2 рутины, `~run_init`, +Imports, снятие ограничения.

> Циклических зависимостей нет: `config` ↛ `init`, `plugin` ↛ `init`, между `config` и `plugin` рёбер нет.

**(4) Body — `run_init` (MODIFIED):** заменить алгоритм (вставлен шаг 3; существующие шаги 3–8 перенумерованы в 4–9) и добавить Requirement. Сигнатура без изменений.

```yaml
"run_init() -> exit_code:int":
  location: init.py
  annotations: |
    Handler for the init command: ensure the goga-project is initialized, build the pybuggy tool config, then bootstrap
    the consumer usages of the api cell into the project where the command is invoked.

    `exit_code`: 0 on success; non-zero goga-init/config-build exit code propagated on failure/cancel.

    Algorithm:
    1. Resolve the output root as the current working directory.
    2. When <cwd>/.goga/config.yml does NOT exist: call `run_goga_init`; if non-zero, return it immediately.
    3. Call `build_pybuggy_config`; if non-zero (cancel/error) return it; on 0 (written or skipped) continue.
    4. Discover every .usages/*.md under the api cell (incl. asserts) from the installed goga_tool_pybuggy.api package.
    5. For each discovered file, write its content to <cwd>/.goga/usages/cooks/pybuggy/<stem>.md.
    6. Register usage keys via `register_usages` with <cwd>/.goga/config.yml (idempotent, skip-existing).
    7. Register annotation lines via `register_annotations` with <cwd>/.goga/config.yml (idempotent by backtick reference).
    8. Log INFO for added, WARNING for skipped.
    9. Return 0.

    Requirements:
    - The config-build step (`build_pybuggy_config`) runs on every call; on user refusal the file is preserved and init continues.
    - The goga-project is initialized at most once; usages/annotations bootstrap is idempotent.

    Constraints:
    - Do not register pybuggy usages/annotations when goga init failed/was cancelled — propagate goga's exit code.
    - Do not copy usages of internal development cells (config, spec, output, matchcrest, plugin, commands).

    Use `run_goga_init`, `build_pybuggy_config`, `register_usages`, `register_annotations`. Use `click` for error mapping. Use `conventions` for logging/testing.
```

**(5) Body — `build_pybuggy_config` (NEW):**

```yaml
"build_pybuggy_config() -> exit_code:int":
  location: init.py
  annotations: |
    Interactive testable-seam that builds <cwd>/.goga/tools/pybuggy/config.yml on every call — the contract test seam
    (public, in __all__). Isolates all TTY prompts; callers/tests stub this routine via monkeypatch (like run_goga_init).

    `exit_code`: 0 on success (file written) or skip (existing file preserved on user "no"); non-zero on cancel/error.

    Algorithm:
    1. Resolve the config path as <cwd>/.goga/tools/pybuggy/config.yml.
    2. When the file already exists: prompt confirm-overwrite (y/N) via `click`; on "no" log INFO and return 0 (skip).
    3. Survey the scalar plugin keys from `PluginConfigKeys` (every member except HEADERS and LOADER): for each prompt one
       value via `click`; BASE_URL required (empty re-prompts — cannot be skipped); the rest optional (empty -> None/skipped).
    4. Survey specs interactively via `click`: for each spec prompt name, type (swagger|openapi), location (required), and
       optional git block (url, location, ref); construct a `SpecEntry` (with `GitEntry` when git given) keyed by name;
       repeat until the user stops, but require AT LEAST ONE spec — the loop re-prompts for the first spec name until one
       is entered (mirrors BASE_URL: a config without specs is invalid per `configuration`/`Config`). Structure per
       `configuration`.
    5. Delegate emission to `write_pybuggy_config` with the config path, the scalar answers (member value -> value|None),
       and the specs mapping.
    6. Return 0. On click.Abort return non-zero; on other Exception log + echo + return non-zero (never raises).

    Requirements:
    - Interactive (TTY via click); tests stub this routine, never the real prompts.
    - BASE_URL mandatory and a Jinja2 template (the comment emitted by write_pybuggy_config must reflect this).
    - At least one spec is required — the survey cannot complete with zero specs (a config without specs is invalid).
    - Returns a code and never raises on cancellation/failure.

    Constraints:
    - Do not write the file on user "no" — preserve the existing file and let init continue.
    - Do not survey HEADERS or LOADER — emitted as commented examples by write_pybuggy_config.
    - Do not duplicate plugin key names — iterate `PluginConfigKeys`.

    Use `click` for prompts/y-N. Use `PluginConfigKeys` for the scalar key set. Use `SpecEntry` and `GitEntry` for specs.
    Use `write_pybuggy_config` for emission. Use `conventions` for logging/type hints/testing.
```

**(6) Body — `write_pybuggy_config` (NEW):**

```yaml
"write_pybuggy_config(path: Path, scalar_values: dict[str, str | None], specs: dict[str, SpecEntry]) -> None":
  location: init.py
  annotations: |
    Pure round-trip emitter of .goga/tools/pybuggy/config.yml from collected answers — active values plus commented
    records for skipped optional scalars and the complex headers/loader sections, and the active specs mapping. No TTY.

    `path`: target file path (<cwd>/.goga/tools/pybuggy/config.yml).
    `scalar_values`: mapping of `PluginConfigKeys` scalar member value -> answered value (str) or None (skipped).
    `specs`: mapping of spec name -> `SpecEntry`.

    Algorithm:
    1. Configure ruamel YAML for round-trip (preserve quotes, key order, comments) and build a fresh CommentedMap.
    2. Iterate scalar members of `PluginConfigKeys` (all except HEADERS, LOADER) in canonical order; for each: value
       present -> active key:value; None -> commented "# key:" line with a one-line explanation.
    3. Emit HEADERS as a commented multi-line example (a "# headers:" block, sample entry, dict note).
    4. Emit LOADER as a commented multi-line example (a "# loader:" block, packages/modules structure, note).
    5. Emit specs mapping as active YAML: name: { type, location, git: { url, location, ref } when present } per
       `SpecEntry`/`GitEntry` shape (see `configuration`).
    6. Ensure parent dir of `path` exists; dump the document.

    Requirements:
    - The emitted document is valid for the config schema (see `configuration`): a specs mapping where each entry carries
      required type/location; scalar plugin keys ignored by Config (extra=ignore), so active/commented presence does not
      break the config cell loader.
    - The specs mapping is always non-empty (`build_pybuggy_config` enforces ≥1 spec) — never emit an empty or absent
      specs section (a config without specs is invalid).
    - Commented records use a leading "#" and a one-line explanation.
    - Output deterministic for the same inputs.

    Constraints:
    - Do not survey/prompt — pure (TTY-free); interactivity lives in build_pybuggy_config.
    - Do not read/merge an existing file — build from scratch and overwrite `path` (confirm is build_pybuggy_config's job).
    - Do not use pyyaml — ruamel.yaml round-trip only.

    Use `ruamel-yaml` for CommentedMap, commented-record emission, dump. Use `PluginConfigKeys` for canonical scalar key
    set/order. Use `SpecEntry`/`GitEntry` for specs shape. Use `configuration` from Imports for schema compatibility.
    Use `conventions` for type hints/relative imports.
```

Существующие типы Body (`run_goga_init`, `register_usages`, `register_annotations`, `init_cmd`) — без изменений.

Шаг команды `pybuggy init`, который на каждом вызове интерактивно строит файл конфигурации инструмента
`.goga/tools/pybuggy/config.yml` (плагинные опции + секция specs). Аудитория — интегратор, подключающий pybuggy,

## Что опрашивается

- Скалярные ключи плагина (источник — `PluginConfigKeys`, скалярные члены): base_url (обязательный, Jinja2-шаблон),

Если `.goga/tools/pybuggy/config.yml` уже существует — выводится подтверждение (y/N). При отказе (N) файл сохраняется,

проверяют YAML.

## Предусловия и побочные эффекты

- Пишет в `<cwd>/.goga/tools/pybuggy/config.yml` (создаёт родительский каталог).
- Сгенерированный файл валиден для config-ячейки (`load_config`/`Config`): присутствует specs, обязательные поля
  `SpecEntry`; скалярные плагинные ключи игнорируются `Config` (extra=ignore).

### Project-level usage file (MODIFY): `.goga/usages/cooks/ruamel-yaml.md`

## Notes

- `goga schema` в окружении нерабочий (AST-ошибки, 379) — структурная верификация выполнена ручным чтением CODEMANIFEST покрываемых ячеек; применять `goga lint`/`goga contract` на этапе apply.
- Декомпозиция рутины (seam `build_pybuggy_config` + чистый writer `write_pybuggy_config`) следует существующему паттерну ячейки `init` (`run_goga_init` vs `register_usages`/`register_annotations`).
- `PluginConfigKeys` — сопутствующее изменение контракта `plugin` (объявление + реэкспорт), не нарушающее Out-of-scope (состав значений enum не меняется).
- `Config`/`load_config` подключены через кросс-ячеечный usage `configuration` (как потребители файла), а не как `Imports.Types` в `init`.
- **Импакт на существующие тесты:** шаг 3 в `run_init` делает вызов `build_pybuggy_config` обязательным на каждом вызове. Все существующие прямые вызовы `run_init` в тестах/скриптах (напр. `tests/commands/init/test_init_integration.py`, который сегодня стабит только `run_goga_init`) должны дополнительно стабить `build_pybuggy_config` (public в `__all__`, monkeypatch), иначе тест уйдёт в TTY. Контракт корня (`goga_tool_pybuggy` импортирует `init_cmd` из `init` и `install` из `plugin`) не затронут — сигнатуры стабильны.
