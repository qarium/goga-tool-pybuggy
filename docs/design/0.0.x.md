# Design Document: `pybuggy-config-init`

> Архитектурная спецификация реализации интерактивного построения `.goga/tools/pybuggy/config.yml`
> командой `pybuggy init`. Документ фиксирует **что** реализовать и **как** — без написания кода и без плана исполнения.
>
> - **Topic:** `pybuggy-config-init`
> - **Ветка / файл:** `0.0.x` → `docs/design/0.0.x.md`
> - **Исходный план:** `docs/arch/0.0.x.md`
> - **Язык:** Python (goga-cell-python), Python 3.10+
> - **Затронутые ячейки:** `goga_tool_pybuggy/commands/init` (корень изменения), `goga_tool_pybuggy/plugin` (контрактное раскрытие `PluginConfigKeys` — уже материализовано на стадии apply).

### New Entities

- **`build_pybuggy_config() -> exit_code:int`** (`init.py`) — интерактивный testable-seam: на каждом вызове опрашивает скалярные плагинные ключи (`PluginConfigKeys` за вычетом `HEADERS`/`LOADER`) и `specs`, делегирует эмиссию `write_pybuggy_config`. Изолирует весь TTY; возвращает код, не бросает. Public, в `__all__` фасада.
- **`write_pybuggy_config(path: Path, scalar_values: dict[str, str | None], specs: dict[str, SpecEntry])`** (`init.py`) — чистый round-trip эмиттер `.goga/tools/pybuggy/config.yml`: активные значения + закомментированные записи (пропущенные необязательные скаляры, `headers`, `loader`) + активная непустая `specs`. Без TTY, детерминирован.
- **`PluginConfigKeys()`** (`plugin.py`) — Entity-декларация существующего enum config-ключей (11 членов); раскрыта как импортируемый контрактный тип и реэкспортирована фасадом `plugin/__init__.py`. **Сопутствующее изменение** (не затрагивает Out-of-scope: состав значений enum неизменен).

### Changed Entities

- **`run_init() -> exit_code:int`** — в алгоритм вставлен **шаг 3** (`build_pybuggy_config`; при ненулевом коде — ранний возврат), прежние шаги 3–8 перенумерованы в 4–9; добавлен `Requirement` о том, что config-build выполняется на каждом вызове (при отказе файл сохраняется, init продолжается). Сигнатура без изменений.
- **Глобальный `Annotations` ячейки `init`** — снято ограничение об отказе от config-ячейки; добавлено указание на `build_pybuggy_config`/`write_pybuggy_config` и на эмиссию `.goga/tools/pybuggy/config.yml`.
- **`Footer.Description`** обеих ячеек — дополнения (см. выше).

## Applied Fixes

### Fixed CODEMANIFEST Defects

— **не требуется.** Фаза валидации контракта (Phase 3 `goga-design-by-changes`) дефектов не выявила.

**Проверенные измерения согласованности (DSL `goga-cell` + принципы `goga-cookbook`):**

1. **Interface ↔ Type.** `write_pybuggy_config(path: Path, scalar_values: dict[str, str | None], specs: dict[str, SpecEntry])` — `Path`/`dict` stdlib-типы (как и в предсуществующих `register_usages(config_path: Path, ...)`; stdlib-типы не требуют `Imports`); `SpecEntry` импортирован из `config`. `build_pybuggy_config` ссылается на `PluginConfigKeys` (импортирован из `plugin`) и `SpecEntry`/`GitEntry` (импортированы из `config`). Все ссылки разрешимы.
2. **Type ↔ Mutation.** Мутаций (`::`) нет — не требуется.
3. **Interface ↔ Interface.** `build_pybuggy_config` → `write_pybuggy_config`: передает `scalar_values: dict[str, str|None]` (ключ = `member.value`) и `specs: dict[str, SpecEntry]` — типы совпадают с сигнатурой `write_pybuggy_config`. `run_init` → `build_pybuggy_config`: ожидает `int` exit-code — совпадает. `write_pybuggy_config` эмитит документ, потребляемый config-ячейкой (`load_config` → `Config`) — совместимость через practice `configuration` (см. трассировку).
4. **Annotations ↔ Entity.** Каждая practice (`conventions`, `click`, `ruamel-yaml`, `goga`, импортированная `configuration`) ссылается хотя бы в одной аннотации. Импортированные типы (`SpecEntry`, `GitEntry`, `PluginConfigKeys`) разрешимы.

**Cross-imports — без циклов:** `init`→`config` (`config` не импортирует `init`), `init`→`plugin` (`plugin` импортирует `api` и `plugin/loaders`, не `init`), рёбер `config`↔`plugin` нет.

**`location`-директивы:** все рутины ячейки `init` — `location: init.py` (тот же уровень каталога, с расширением, без обхода родителя). `PluginConfigKeys` — `location: plugin.py`. Корректно.

**Lint-верификация (`goga lint`)** по обеим ячейкам возвращает ровно две категории находок:
- `[usage_filepath_exists]` и `[import_has_valid_from_path]`.

Обе категории — **окружение-артефакты**, не дефекты контракта: линтер резолвит пути `Usages` и `From:` относительно каталога ячейки, а не корня проекта, тогда как DSL требует разрешения от корня проекта, и все файлы реально существуют (`/workspace/.goga/usages/conventions.md`, `.goga/usages/cooks/click.md`, `…/ruamel-yaml.md`, `…/goga.md`, каталоги `goga_tool_pybuggy/{api,config,plugin,plugin/loaders}`). Это известное ограничение окружения (см. `Notes` плана `docs/arch/0.0.x.md` и summary стадии apply: `goga schema` нерабочий — AST-ошибки 379). **Правок CODEMANIFEST не выполнялось**: пути корректны по DSL, их изменение сломало бы контракт. Структурная верификация выполнена `goga lint` (категории) + ручным чтением CODEMANIFEST против DSL.

### Data Flows

**Сценарий A — построение `config.yml` (каждый вызов `init`):**
1. `run_init` → `build_pybuggy_config()`.
2. `build_pybuggy_config` опрашивает (click): скалярные ключи → `scalar_values: dict[str, str|None]` (ключ = `PluginConfigKeys.<member>.value`); specs → `specs: dict[str, SpecEntry]` (≥1 запись).
3. `build_pybuggy_config` → `write_pybuggy_config(path, scalar_values, specs)`.
4. `write_pybuggy_config` эмитит `CommentedMap` (активные ключи + закомментированные записи, активная `specs`) и dump в `<cwd>/.goga/tools/pybuggy/config.yml`.
5. Файл потребляется config-ячейкой (`load_config` → `Config`): `specs` валидируется, скалярные плагинные ключи игнорируются (`Config.model_config = ConfigDict(kw_only=True)` → pydantic v2 default `extra="ignore"`).

**Сценарий B — пропуск построения (файл существует, отказ):**
1. `run_init` → `build_pybuggy_config()`.
2. Файл существует → click-confirm (y/N); пользователь «N» → log INFO, `return 0` (skip), файл сохранён.
3. `run_init` шаг 3 получает 0 → продолжает bootstrap usages (шаги 4–9).

**Сценарий C — отмена/ошибка построения:**
1. `build_pybuggy_config` ловит `click.Abort` / `Exception` → log + return ненулевой.
2. `run_init` шаг 3 получает ненулевой → ранний возврат (usages не регистрируются).

**Сценарий D — уже существующие рутины:** `run_goga_init`, `register_usages`, `register_annotations`, discovery — без изменений; шаг 3 лишь встроен между goga-init и bootstrap usages.

### Entity Dependencies

- **`run_init`** зависит от `run_goga_init`, `build_pybuggy_config`, `register_usages`, `register_annotations`, `_discover_usages` (все в `init.py`).
- **`build_pybuggy_config`** зависит от `write_pybuggy_config`, `PluginConfigKeys` (импорт из `plugin`), `SpecEntry`/`GitEntry` (импорт из `config`), `click`.
- **`write_pybuggy_config`** зависит от `PluginConfigKeys` (канонический порядок скаляров), `SpecEntry`/`GitEntry` (форма specs), `ruamel.yaml`, practice `configuration`.
- **Порядок реализации (leaves→root):** `config` (provider, готов) → `plugin` (`PluginConfigKeys` раскрыт, готов) → `init` (build `build_pybuggy_config`/`write_pybuggy_config` + шаг 3 в `run_init` + фасад).

### Trace: `write_pybuggy_config(path, scalar_values, specs)`

#### Chain
1. **Input**: `path: Path` (цель), `scalar_values: dict[str, str|None]` (`PluginConfigKeys.<scalar>.value -> ответ|None`), `specs: dict[str, SpecEntry]` (≥1).
2. **Step 1**: `yaml = YAML(); yaml.preserve_quotes = True`; `doc = CommentedMap()`. → checkpoint: ruamel round-trip, passed.
3. **Step 2–4 (построение ordered-сегментов по каноническому порядку enum)**. Канонический порядок: `BASE_URL, HEADERS, TIMEOUT, DATA_KEY, ERROR_KEY, RETRIES, LOADER, ASSERT_TIMEOUT, ASSERT_DELAY, ASSERT_FIELD_CLASS, ASSERT_RESPONSE_CLASS`, затем `specs`. Каждый член классифицируется как ACTIVE (`scalar_values[member.value]` не None) или COMMENTED (None / комплексный член `HEADERS`/`LOADER`):
   - **Алгоритм pending-comments**: поддерживается буфер `pending: list[str]`. Для каждого члена:
     - ACTIVE → `doc[member.value] = value`; если `pending` непуст — `doc.yaml_set_comment_before_after_key(member.value, before="\n".join(pending))`, очистить `pending`; для `BASE_URL` дополнительно `doc.yaml_add_eol_comment("required, Jinja2 template", "base_url")`.
     - COMMENTED → добавить текст записи/блока в `pending`.
   - `HEADERS` → многострочный закомментированный блок (пример dict) в `pending`.
   - `LOADER` → многострочный закомментированный блок (packages/modules) в `pending`.
   → checkpoint: **механизм эмпирически подтверждён** (см. Algorithm Design + Verification ниже): `yaml_set_comment_before_after_key` крепит комментарий к **следующему** активному ключу; терминальный якорь `specs` (всегда ACTIVE) гарантирует вывод всех trailing-комментариев. passed.
4. **Step 5 (specs — активный YAML, терминальный якорь)**: `doc["specs"] = CommentedMap()`; для каждого `(name, entry)`: вложенный `CommentedMap` с `type`, `location`, и `git: CommentedMap(url, location, ref)` при `entry.git is not None`; перед вставкой `specs` — сбросить `pending` как `before` к `specs`. → checkpoint: форма совпадает с `SpecEntry`/`GitEntry`; порядок specs = порядок вставки (детерминирован). passed.
5. **Step 6**: `path.parent.mkdir(parents=True, exist_ok=True); yaml.dump(doc, path)`. → **Output**: валидный YAML-документ; активные ключи (скаляры) — extra для `Config` (ignored); `specs` — валидируется; закомментированные записи — YAML-комментарии (выбрасываются `yaml.safe_load`, отсутствуют в `keys()`). Детерминирован для тех же входов.

#### Checkpoint Summary
- `yaml_add_eol_comment` для `base_url` — trailing `# required, Jinja2 template` (требование `Requirements` build_pybuggy_config): **passed**.
- Comment-attachment к следующему активному ключу, `specs` как терминальный якорь: **passed** (эмпирически).
- Jinja2-значение `base_url` (напр. `https://{{ host }}/api`) выгружается plain-скаляром без кавычек: **passed** (эмпирически).
- Reload возвращает только активные ключи → `Config` игнорирует скалярные плагинные ключи (extra=ignore): **passed** (эмпирически).
- `specs` всегда присутствует и непуста (по контракту `build_pybuggy_config`): **passed**.

## Algorithm Design

### `run_init()` — MODIFIED

**Responsibility**: оркестратор команды `pybuggy init`: обеспечить инициализацию goga-проекта, построить `config.yml`, затем bootstrap consumer-usages ячейки `api`.

**Algorithm:**
```
1. cwd = Path.cwd()                                        — корень вывода
   → cwd
2. IF NOT (cwd/.goga/config.yml).exists():
   - rc = run_goga_init()
   - IF rc != 0: return rc                                 — отмена/ошибка goga → ранний возврат
   → (goga-проект инициализирован)
3. rc = build_pybuggy_config()                             — НОВЫЙ шаг (каждый вызов)
   - IF rc != 0: return rc                                 — отмена/ошибка config-build → ранний возврат
   → (.goga/tools/pybuggy/config.yml готов или пропущен)
```

### `build_pybuggy_config()` — NEW

**Responsibility**: интерактивный testable-seam построения `.goga/tools/pybuggy/config.yml`; изолирует весь TTY.

**Algorithm:**
```
config_path = Path.cwd() / ".goga" / "tools" / "pybuggy" / "config.yml"
try:
  1. IF config_path.exists():
     - IF NOT click.confirm("Overwrite existing config?", default=False):
         logger.info("config build skipped", extra={"path": str(config_path)})
         return 0                                     — skip, файл сохранён
  2. scalar_values = {}                                — ключ = PluginConfigKeys.<member>.value
     FOR member IN PluginConfigKeys (order = enum order, skip HEADERS, LOADER):
       - IF member is BASE_URL:
           WHILE NOT (val := click.prompt("base_url (required, Jinja2 template)").strip()):
               click.echo("base_url is required")      — переспрос, нельзя пропустить
           scalar_values[member.value] = val
       - ELSE:
           val = click.prompt(member.value, default="", show_default=False).strip()
           scalar_values[member.value] = val or None   — пусто → None (skipped)
  3. specs = {}
     first = True
     WHILE True:
       name = click.prompt("spec name" + ("" if first else " (empty to finish)"), default="" if not first else None).strip()
       IF first:
         WHILE NOT name: name = click.prompt("spec name (required)").strip()    — минимум одна spec
       ELIF not name:
         break
       t = click.prompt("type", type=click.Choice(["swagger","openapi"]))
       location = click.prompt("location").strip()
       WHILE NOT location: location = click.prompt("location (required)").strip()
       git = None
       IF click.confirm("Add git source?", default=False):
         g_url = click.prompt("git url").strip()
         g_loc = click.prompt("git location").strip()
         g_ref = click.prompt("git ref (optional)", default="").strip() or None
         git = GitEntry(url=g_url, location=g_loc, ref=g_ref)
       specs[name] = SpecEntry(type=t, location=location, git=git)
       first = False
  4. write_pybuggy_config(config_path, scalar_values, specs)
  5. return 0
except click.Abort:
  return <non-zero>                                    — отмена (Ctrl-C)
except Exception as exc:
  logger.error("config build failed", extra={"error": str(exc)})
  click.echo(f"Error: {exc}", err=True)
  return <non-zero>                                    — никогда не бросает
```

> Ненулевой код на отмену/ошибку — константа, зеркалит `run_goga_init` (там `1`). Решение: `1` (единообразие в ячейке).

**Errors:** `click.Abort` → return ненулевой; прочие `Exception` → log + echo + return ненулевой. Никогда не бросает (контракт: `run_init` вызывает вне try/except).

**Edge Cases:** существующий файл + отказ → 0 (skip); пустой опциональный скаляр → `None` (закомментирован эмиттером); первая spec без имени — переспрос (≥1 обязательно); `git.ref` пуст → `None`.

### `write_pybuggy_config(path, scalar_values, specs)` — NEW

**Responsibility**: чистый round-trip эмиттер `.goga/tools/pybuggy/config.yml` из собранных ответов; активные значения + закомментированные записи + активная непустая `specs`.

**Algorithm (механизм pending-comments, эмпирически подтверждён):**
```
yaml = YAML(); yaml.preserve_quotes = True
doc = CommentedMap()
pending = []                                            — буфер закомментированных записей

# HEADERS — всегда COMMENTED (комплексный член, не опрашивается)
HEADERS_BLOCK = ("headers: example (skipped complex member)\n"
                 "  X-Example: value\n"
                 "  default request headers dict")

# LOADER — всегда COMMENTED (комплексный член, не опрашивается)
LOADER_BLOCK = ("loader: example (skipped complex member)\n"
                "  packages:\n"
                "    - api\n"
                "  modules: []")

def _flush(key):
    """Attach pending comments as `before` to the active `key`; clear buffer."""
    if pending:
        doc.yaml_set_comment_before_after_key(key, before="\n".join(pending))
        pending.clear()

# 1. Канонический проход по enum (BASE_URL .. ASSERT_RESPONSE_CLASS), skip HEADERS/LOADER handled below
CANONICAL = [m for m in PluginConfigKeys]                — порядок объявления
COMPLEX = {PluginConfigKeys.HEADERS, PluginConfigKeys.LOADER}
for member in CANONICAL:
    if member in COMPLEX:
        pending.append(HEADERS_BLOCK if member is PluginConfigKeys.HEADERS else LOADER_BLOCK)
        continue
    val = scalar_values.get(member.value)               — str | None
    if val is None:
        pending.append(f"{member.value}: (skipped optional scalar)")
    else:
        doc[member.value] = val                          — ACTIVE
        _flush(member.value)                             — крепим pending к этому активному ключу
        if member is PluginConfigKeys.BASE_URL:
            doc.yaml_add_eol_comment("required, Jinja2 template", "base_url")

# 2. specs — активный терминальный якорь (всегда присутствует, ≥1 по контракту)
specs_map = CommentedMap()
for name, entry in specs.items():                        — порядок = порядок вставки (детерминирован)
    sp = CommentedMap()
    sp["type"] = entry.type
    sp["location"] = entry.location
    if entry.git is not None:
        g = CommentedMap()
        g["url"] = entry.git.url
        g["location"] = entry.git.location
        g["ref"] = entry.git.ref
        sp["git"] = g
    specs_map[name] = sp
doc["specs"] = specs_map
_flush("specs")                                          — крепим остаток pending (trailing-комментарии) к specs

# 3. dump
path.parent.mkdir(parents=True, exist_ok=True)
yaml.dump(doc, path)
```

**Почему `_flush`/pending работает:** ruamel `yaml_set_comment_before_after_key(key, before=...)` выводит строки `# ...` **непосредственно перед** ключом `key`; вызывается **после** того, как `key` уже вставлен в `CommentedMap`. Каждая закомментированная запись/блок таким образом визуально размещается в позиции следующего активного ключа. Так как `specs` всегда ACTIVE (≥1 по контракту), любой trailing-буфер (напр. пропущенные `ASSERT_*` после последнего активного скаляра, либо сами `HEADERS`/`LOADER`-блоки, если все скаляры пропущены) гарантированно выводится перед `specs`. **Эмпирически подтверждено** (см. Verification).

**Errors:** pure — I/O-ошибки dump/`mkdir` (`OSError`) и ошибки ruamel (`YAMLError`) **пропагируются** вызывающему (`build_pybuggy_config` ловит `Exception` → ненулевой код).

**Edge Cases:**
- Все опциональные скаляры пропущены → все они уйдут в `pending` и крепятся к `specs`; документ содержит только `base_url` (active) + `# ...` комментарии + `specs`.
- spec без git → блок `git` опускается.
- Несколько specs → все выведены в порядке вставки.
- `base_url` = Jinja2-шаблон с `{{ }}` → выгружается plain-скаляром (без кавычек); эмпирически подтверждено.
- Детерминизм: тот же `scalar_values` + тот же порядок `specs` → байт-идентичный вывод.

**Verification (эмпирическая, ruamel 0.19.1 под system python3.12):** выполнен тестовый прогон с `base_url=https://{{ host }}/api`, активными `timeout`/`data_key`/`retries`, пропущенными `error_key`/`assert_timeout`/`assert_delay`/`assert_field_class`/`assert_response_class`, блоками `headers`/`loader`, specs с git-блоком. Вывод (механизм `_flush` сбрасывает `pending` перед **каждым** активным скаляром, поэтому `# headers:` крепится к ближайшему следующему активному ключу — `timeout`, — а не копится перед `specs`; `specs` остаётся терминальным якорем только для trailing-буфера — `# loader:` + пропуски `assert_*`):
```
base_url: https://{{ host }}/api  # required, Jinja2 template
# headers: example (skipped complex member)
#   X-Example: value
#   default request headers dict
timeout: '30'
data_key: data
# error_key: (skipped optional scalar)
retries: '2'
# loader: example (skipped complex member)
#   packages:
#     - api
#   modules: []
# assert_timeout: (skipped optional scalar)
# assert_delay: (skipped optional scalar)
# assert_field_class: (skipped optional scalar)
# assert_response_class: (skipped optional scalar)
specs:
  api:
    type: openapi
    location: specs/api.yaml
    git:
      url: https://example.com/specs.git
      location: api.yaml
      ref: main
```
Reload (`yaml.load`) возвращает ключи `['base_url','timeout','data_key','retries','specs']` — закомментированные записи **не** становятся ключами. `Config.model_validate` возьмёт `specs`, проигнорирует скалярные плагинные ключи (extra=ignore).

## Cross-cutting Concerns

- **Error handling (глобальная стратегия ячейки):** интерактивные seam-рутины (`run_goga_init`, `build_pybuggy_config`) возвращают exit-code и **никогда не бросают** (`click.Abort` и `Exception` → ненулевой код + log/echo); `run_init` вызывает их вне try/except и пропагирует код. Bootstrap-ошибки файлового I/O/YAML/навигации в `run_init` маппятся в `click.ClickException`. `write_pybuggy_config` (pure) пропагирует `OSError`/`YAMLError` вызывающему `build_pybuggy_config`.
- **Logging:** структурированный `logging` (`logger = logging.getLogger(__name__)`), lowercase-сообщения, контекстные `extra`. INFO — skip при отказе перезаписи (`build_pybuggy_config`); INFO (added) / WARNING (skipped) — в `run_init` шаг 8 (существующее). ERROR + `click.echo` — на сбой config-build (как в `run_goga_init`). Секретов/токенов в логах нет (правило conventions).
- **Validation:**
  - `BASE_URL` непустой — enforced циклом переспроса (`build_pybuggy_config`).
  - ≥1 spec — enforced (первое имя переспрашивается).
  - `type ∈ {swagger, openapi}` — `click.Choice` (соответствует `SpecEntry.type: Literal`).
  - `location` непустой — enforced.
  - git-блок: `url`/`location` обязательны при выборе git; `ref` опционален → `None`.
  - Валидность для config-схемы — конструктивная: `write_pybuggy_config` эмитит `specs` по форме `SpecEntry`/`GitEntry`; скалярные плагинные ключи extra=ignore для `Config`.
- **Caching:** не требуется (каждый вызов пересобирает файл).
- **Concurrency:** не требуется (однопоточный CLI).

## Additional Instructions for the Implementation Agent

1. **Фасад `init/__init__.py`**: добавить `build_pybuggy_config`, `write_pybuggy_config` в импорт из `.init` и в `__all__` (правило goga-cell-python: фасад экспонирует полный контракт через `__all__`). Контракт `build_pybuggy_config` объявляет её public в `__all__`; `write_pybuggy_config` нужна для прямого тестирования эмиссии. Проверка фасада: `python -c "from goga_tool_pybuggy.commands.init import build_pybuggy_config, write_pybuggy_config"`.

2. **Импорты в `init.py`**: относительные — `from ..config import GitEntry, SpecEntry`; `from ..plugin import PluginConfigKeys` (правило conventions). Type-hints: `from pathlib import Path` (уже есть), `dict[str, str | None]`, `SpecEntry`.

3. **Канонический порядок скаляров = порядок объявления `PluginConfigKeys`**: НЕ хардкодить список ключей — итерировать `PluginConfigKeys` (фильтр `HEADERS`/`LOADER`); и `build_pybuggy_config`, и `write_pybuggy_config` используют один источник — отсутствие дублирования (контракт).

4. **Механизм pending-comments в `write_pybuggy_config`** (см. Algorithm Design): `_flush(key)` крепит буфер через `doc.yaml_set_comment_before_after_key(key, before="\n".join(pending))` **после** вставки активного `key`; `specs` — обязательный терминальный якорь (`_flush("specs")` в конце). Без якоря trailing-комментарии НЕ выводятся. Тексты закомментированных записей передавать **без** ведущего `#` (ruamel добавляет `# ` сам). Эмпирически подтверждено.

5. **`base_url` eol-комментарий**: `doc.yaml_add_eol_comment("required, Jinja2 template", "base_url")` — требование `Requirements` `build_pybuggy_config`.

6. **Ненулевой код `build_pybuggy_config`**: `1` на `click.Abort`/`Exception` (зеркало `run_goga_init`); единообразие в ячейке.

7. **`specs` всегда непуста**: по контракту `build_pybuggy_config` гарантирует ≥1. `write_pybuggy_config` не проверяет/не падает на пустой `specs` — это контрактная обязанность вызывающего (аннотировано).

8. **Не использовать pyyaml** в `write_pybuggy_config` — только `ruamel.yaml` round-trip (Constraint).

9. **Тесты — обновить существующие**: всем прямым вызовам `run_init()`/`init_cmd` в `tests/commands/init/{test_init.py,test_init_integration.py}` добавить стаб `build_pybuggy_config` (monkeypatch `→0`), кроме тестов, возвращающихся на шаге 2 до шага 3 (`test_run_init_propagates_goga_cancel_without_registering`, `test_init_cmd_propagates_goga_cancel_without_writing_usages`, `test_init_cmd_propagates_exit_code_via_ctx`). См. Test Stack Trace.

10. **Фасад plugin** (`plugin/__init__.py`) — уже реэкспортирует `PluginConfigKeys` (стадия apply); изменений не требуется. Проверка: `python -c "from goga_tool_pybuggy.plugin import PluginConfigKeys"`.

11. **Out-of-scope**: код `plugin.py` и состав enum `PluginConfigKeys` не меняются; config-ячейка — UNCHANGED provider; `Config`/`load_config` подключены через кросс-ячеечный usage `configuration` (как потребители файла), не как `Imports.Types` в `init`.

12. **Acceptance-проверки** (из плана `docs/arch/0.0.x.md` § Verification Checklist / Acceptance Criteria) — все релевантные покрыты тест-сценариями выше: создание файла на каждом вызове; подтверждение (y/N) с сохранением при отказе; обязательный `base_url`; пропущенные поля закомментированы; `headers`/`loader` — закомментированные примеры; `specs` интерактивно (несколько, type/location обязательны, git опционален); заполненный конфиг проходит `load_config()`; ключи из `PluginConfigKeys` без дублирования; интерактив изолирован в `build_pybuggy_config`.
