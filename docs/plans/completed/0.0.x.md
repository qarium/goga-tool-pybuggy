# Plan: `pybuggy-config-init` (branch `0.0.x`)

## Purpose

Реализовать интерактивное построение `.goga/tools/pybuggy/config.yml` командой `pybuggy init` на каждом вызове.

После реализации ячейка `goga_tool_pybuggy/commands/init` (`init.py`) должна предоставлять:

- **`write_pybuggy_config(path, scalar_values, specs)`** — чистый round-trip эмиттер `config.yml`: активные значения + закомментированные записи (пропущенные необязательные скаляры, `headers`, `loader`) + активная непустая `specs`. Без TTY, детерминирован.
- **`build_pybuggy_config() -> exit_code:int`** — интерактивный testable-seam: опрашивает скалярные плагинные ключи (`PluginConfigKeys` за вычетом `HEADERS`/`LOADER`) и `specs`, делегирует эмиссию `write_pybuggy_config`. Изолирует весь TTY; возвращает код, не бросает.
- **`run_init()`** (модификация) — в алгоритм встроен новый шаг 3 (`build_pybuggy_config`; при ненулевом коде — ранний возврат), прежние шаги 3–8 перенумерованы в 4–9.

Оба новых имени должны быть импортируемы с фасада `goga_tool_pybuggy.commands.init` и входить в `__all__`.

**Главные разрывы контракт ↔ код:**

1. `build_pybuggy_config` и `write_pybuggy_config` отсутствуют в `init.py` и в фасаде `__all__`.
2. `run_init` не содержит шага построения `config.yml`.
3. Существующие тесты `run_init()`/`init_cmd`, доходящие до discovery, уйдут в TTY-промпт после добавления шага 3 — требуют стаба `build_pybuggy_config`.
4. Отсутствуют тесты эмиссии (`write_pybuggy_config`) и интерактива (`build_pybuggy_config`).

**Стратегия реализации:** leaves → root внутри ячейки `init`:

1. `write_pybuggy_config` (чистый лист — зависит только от импортов `PluginConfigKeys`/`SpecEntry`/`GitEntry`/`ruamel.yaml`).
2. `build_pybuggy_config` (зависит от `write_pybuggy_config`).
3. `run_init` шаг 3 (зависит от `build_pybuggy_config`) + обновление 7 существующих тестов + новый тест пропагации.
4. Интеграционные тесты (кросс-ячеечная совместимость init↔config + сквозная цепочка).

Ячейки `plugin` (`PluginConfigKeys` уже раскрыт контрактом и реэкспортирован фасадом — стадия apply) и `config` (UNCHANGED provider) — **без изменений**, задач для них нет.

    if pending:
        doc.yaml_set_comment_before_after_key(key, before="\n".join(pending))
        pending.clear()

CANONICAL = [m for m in PluginConfigKeys]                — порядок объявления

for member in CANONICAL:
    if member in COMPLEX:
        pending.append(HEADERS_BLOCK if member is PluginConfigKeys.HEADERS else LOADER_BLOCK)
        continue
    val = scalar_values.get(member.value)               — str | None
    if val is None:
        pending.append(f"{member.value}: (skipped optional scalar)")
    else:
        doc[member.value] = val                          — ACTIVE
        _flush(member.value)                             — крепим pending к этому активному ключу
        if member is PluginConfigKeys.BASE_URL:
            doc.yaml_add_eol_comment("required, Jinja2 template", "base_url")

specs_map = CommentedMap()
for name, entry in specs.items():                        — порядок = порядок вставки (детерминирован)

        g["url"] = entry.git.url
        g["location"] = entry.git.location
        g["ref"] = entry.git.ref
        sp["git"] = g
    specs_map[name] = sp
doc["specs"] = specs_map
_flush("specs")                                          — крепим остаток pending (trailing) к specs

path.parent.mkdir(parents=True, exist_ok=True)
yaml.dump(doc, path)
