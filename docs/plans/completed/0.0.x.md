# Plan: `0.0.x` — `pybuggy init`: генерация корневого `conftest.py`

## Purpose

Реализовать генерацию корневого `conftest.py` целевого проекта командой `pybuggy init` (ветка `0.0.x`).

После реализации:
- команда `pybuggy init` создаёт `<cwd>/conftest.py` из фиксированного шаблона
  (`load_dotenv()` → `plugin.install()`), проводя пользователя через гейт перезаписи
  (`click.confirm`, `default=False`), единообразный с гейтами конфигов;
- в фасаде ячейки `goga_tool_pybuggy/commands/init` публично доступна чистая (TTY-free) рутина
  `write_pybuggy_conftest(path: Path)`;
- сбой записи conftest логируется (ERROR) и мапится в `click.ClickException` (ненулевой exit);
  отказ от перезаписи — INFO-лог и пропуск шага (exit 0, файл не тронут).

Главные разрывы между контрактом и кодом:
- контрактуя сущность `write_pybuggy_conftest(path: Path)` (Routine, `location: init.py`)
  не соответствует ни строчка кода — рутины и константы `_CONFTEST_TEMPLATE` нет;
- `run_init` не выполняет шаг 9 (генерация conftest) — оркестратор завершается сразу после
  `_log_registration` (шаг 8) инструкцией `return 0`;
- фасад не экспортирует `write_pybuggy_conftest`.

Общая стратегия реализации: чистый писатель + гейт в оркестраторе (зеркально существующей паре
`build_pybuggy_config` → `write_pybuggy_config`); решение о перезаписи вынесено в private-хелпер
`_write_root_conftest` (паттерн `_should_rebuild`/`_log_registration`), что удерживает `run_init`
под mccabe-капом 10. Порядок материализации leaf → root: константа → Routine → хелпер →
оркестратор → фасад. TDD: контракт-тесты до кода, логик-тесты после.

    шаблона; «wires the pybuggy plugin into the consumer's pytest run»;

### Task 1: Routine `write_pybuggy_conftest` + константа `_CONFTEST_TEMPLATE` + экспорт на фасаде

Контекст: реализация новой контрактной сущности `write_pybuggy_conftest(path: Path)` (Routine,
`location: init.py`) — чистого (TTY-free) эмиттера корневого `conftest.py` целевого проекта из
фиксированного захардкоженного шаблона. Всегда (пере)записывает `path`, без проверки
существования и без подтверждений (`OSError` намеренно распространяется к вызывающему — паттерн
`install_pybuggy`). Порядок материализации внутри задачи: константа `_CONFTEST_TEMPLATE` → Routine
→ фасад. Файлы: `goga_tool_pybuggy/commands/init/init.py`,
`goga_tool_pybuggy/commands/init/__init__.py`, `tests/commands/init/test_init.py`.

Текст шаблона (единственный источник — модульная константа; дословно, с завершающим `\n`;
совпадает с CODEMANIFEST-аннотацией, `init.md` и `enable.md`):

```python
_CONFTEST_TEMPLATE = (
    "from dotenv import load_dotenv\n"
    "\n"
    "load_dotenv()\n"
    "\n"
    "from goga_tool_pybuggy import plugin\n"
    "\n"
    "plugin.install()\n"
)
```

Алгоритм рутины (из CODEMANIFEST / дизайн-документа):

```
1. path.parent.mkdir(parents=True, exist_ok=True)
   → родительский каталог существует
2. path.write_text(_CONFTEST_TEMPLATE, encoding="utf-8")
   → файл path перезаписан дословным шаблоном (безусловно, на каждом вызове)
```

Edge cases рутины: существующий файл → молча перезаписывается (проверка существования — не здесь);
вложенный путь (`tmp_path/"nested"/"conftest.py"`) → каталог создаётся шагом 1; пустой TTY-контекст
→ не влияет: ни одного вызова `click.*` внутри рутины.

Общий тест-сетап (локальная константа в `test_init.py`, дословно):
