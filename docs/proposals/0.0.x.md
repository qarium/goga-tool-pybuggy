# Задача: `pybuggy init` — генерация корневого `conftest.py` целевого проекта

## Current State

Плагин pybuggy включается в тестовый набор потребителя только явным вызовом
`goga_tool_pybuggy.plugin.install()` из корневого `conftest.py` целевого проекта — import-time
auto-wiring отсутствует (`goga_tool_pybuggy/plugin/.usages/enable.md`). Раньше этот файл создавал скилл
`pybuggy-api-automate-conftest` (stage `setup-conftest` automate-пайплайна), удалённый коммитом `da5603d`;
после удаления conftest.py в проекте потребителя не создаёт никто.

Команда `pybuggy init` (ячейка `goga_tool_pybuggy/commands/init`) сегодня создаёт: `.goga/config.yml`
(in-process goga-init), `.goga/Dockerfile` с дописанной install-строкой, `.goga/tools/pybuggy/config.yml`
и bootstrap usages api-ячейки (копирование + регистрация ключей и аннотаций). Корневой `conftest.py` не
создаётся — после init тестовый набор потребителя не получает фикстуру `api` без ручного шага.

## Description

Дополнить `pybuggy init` финальным шагом: создавать корневой `conftest.py` целевого проекта по пути
`<cwd>/conftest.py` (тот же корень вывода, что и остальные артефакты `run_init`), чтобы инфраструктура
запуска тестов появлялась той же командой, что инициализирует остальной goga-проект.

Содержимое файла — фиксированный шаблон, записываемый дословно (аналог жёсткой install-строки у
Dockerfile-шага), без параметризации. Семантика шаблона (дословная форма — в ADR-приложении ниже,
раздел «Решённые детали»):

- вызов `load_dotenv()` без аргументов (поведение по умолчанию `override=False` — CI/оператор может
  фиксировать окружение);
- затем импорт `plugin` из `goga_tool_pybuggy` и вызов `plugin.install()`;
- порядок «load_dotenv до install» обязателен: опции плагина резолвятся из `os.environ`.

Поведение при существующем файле — зеркально пересозданию `.goga/config.yml` и tool-конфига в `run_init`:
перезапись только через подтверждение (по умолчанию отказ); при отказе шаг пропускается с INFO-логом,
остаток init завершается успешно. Ошибка записи — лог + non-zero exit, как у остальных шагов.

## Scope

**In scope:**

- Новый финальный шаг алгоритма `run_init` (после bootstrap usages): гейт существования/подтверждения
  перезаписи `<cwd>/conftest.py` и вызов процедуры записи.
- Чистая процедура записи conftest в ячейке `commands/init`: всегда пишет переданный путь, без TTY,
  без проверок существования (шов в духе `build_pybuggy_config` → `write_pybuggy_config`; размещение
  решено ADR — отдельная ячейка не заводится).
- Обновление CODEMANIFEST ячейки `commands/init`: новая сигнатура процедуры, обновление алгоритма и
  описаний `run_init` и ячейки.
- Обновление `goga_tool_pybuggy/plugin/.usages/enable.md`: указание, что `pybuggy init` генерирует
  conftest автоматически; ручной путь включения сохраняется для проектов без init и приводится к тому же
  шаблону, что и генерируемый файл (`load_dotenv()` → `install()`), чтобы документированный ручной путь
  не расходился с генерируемым conftest (опции плагина резолвятся из `os.environ`).
- Краткое дополнение `goga_tool_pybuggy/commands/init/.usages/init.md`: conftest.py в списке артефактов
  команды и в предусловиях/побочных эффектах (расширение ADR, подтверждено на этапе propose).
- Дополнение `.goga/usages/cooks/click.md` секцией про интерактивные запросы (`click.confirm`/
  `click.prompt`) — гейт перезаписи conftest использует тот же паттерн, что и существующие гейты
  `run_init` (расширение по итогам review, подтверждено пользователем).
- Unit-тесты новых веток в зеркальной структуре `tests/`.

**Out of scope:**

- Merge с существующим conftest.py (маркер-проверка + дописывание блока) — отклонено ADR; пользователь
  объединяет код вручную при отказе от перезаписи.
- Отдельная ячейка или размещение процедуры в ячейке `plugin` — отклонено ADR (plugin — runtime pytest,
  генерация файлов проекта — bootstrap-зона `commands/init`).
- Параметризация шаблона (флаги, переменные, версии) — шаблон жёстко фиксирован в коде init.
- Проверка наличия `goga_tool_pybuggy` / `python-dotenv` в окружении pytest — отсутствие проявится при
  запуске тестов потребителя.
- Правка `skills/pybuggy/SKILL.md` — отклонено ADR, достаточно usage-документации.
- Изменения automate-пайплайна и восстановление удалённого скилла.

## Acceptance Criteria

- В свежем проекте после `pybuggy init` существует `<cwd>/conftest.py`, содержимое которого дословно
  равно фиксированному шаблону из ADR (порядок операторов: load_dotenv → импорт plugin → install).
- При существующем `<cwd>/conftest.py` запрашивается подтверждение перезаписи с отказом по умолчанию;
  отказ → файл не изменён, шаг пропущен с INFO-логом, команда завершается exit 0.
- Подтверждение → файл перезаписан шаблоном.
- Ошибка записи → лог + non-zero exit (поведение единообразно с остальными шагами `run_init`).
- Шаг выполняется последним в алгоритме `run_init` (после bootstrap usages) и не выполняется, если
  init завершился ошибкой/отменой ранее.
- Процедура записи доступна программно (фасад ячейки), всегда пишет файл, не интерактивна, не проверяет
  существование — тестируется напрямую без TTY.
- Повторный запуск `pybuggy init` при отказе от перезаписи не изменяет существующий conftest.py и не
  ломает идемпотентность остальных шагов.
- CODEMANIFEST ячейки `commands/init` валиден по DSL (`goga lint`) и отражает новую процедуру и шаг.
- `plugin/.usages/enable.md` документирует автогенерацию conftest командой init; ручной путь включения
  приведён к тому же шаблону, что и генерируемый файл (`load_dotenv()` → `install()`);
  `commands/init/.usages/init.md` упоминает conftest.py среди артефактов и побочных эффектов;
  `.goga/usages/cooks/click.md` содержит секцию про интерактивные запросы (confirm с `default=False`,
  prompt).
- Новые ветки покрыты unit-тестами (отсутствие файла / подтверждённая перезапись / отказ → пропуск /
  ошибка записи → non-zero); `pytest tests/ -x` и `ruff check` проходят в виртуальном окружении.

## Stack

- **Язык:** Python 3.10+ (конвенция проекта, без изменений).
- **Библиотеки:** существующие — `click` (интерактивный confirm гейта в `run_init`); stdlib `pathlib`,
  `logging`. Новые библиотеки не вводятся.
- **Инфраструктура:** не затрагивается.

## External Dependencies

Новые внешние зависимости отсутствуют. Runtime-зависимости целевого проекта, на которые ссылается
шаблон (`goga_tool_pybuggy`, `python-dotenv`), уже являются зависимостями pybuggy (`pyproject.toml`).

| Компонент | Usage-файл | Статус |
|-----------|------------|--------|
| click | `.goga/usages/cooks/click.md` | updated — дополняется секцией про интерактивные запросы (`click.confirm`/`click.prompt`) под гейт перезаписи conftest |
| python-dotenv | `.goga/usages/cooks/python-dotenv.md` | existing — покрывает `load_dotenv()` без аргументов / `override=False`, обновление не требуется |

Изменения в cooks: `.goga/usages/cooks/click.md` дополняется секцией про интерактивные запросы

## Risks and Constraints

- Существующий кастомный `conftest.py` никогда не мержится и не перезаписывается молча: либо
  подтверждённая замена, либо пропуск. Сознательное отступление от инварианта удалённого скилла —
  «починить» merge в будущем не надо.
- Шаблон жёстко фиксирован в коде init и не параметризуется (как версия `0.1.x` в Dockerfile-строке);
  изменения шаблона — правкой кода.
- Порядок «load_dotenv до install» и безаргументный вызов `load_dotenv()` (`override=False`) — часть
  контракта шаблона, нарушение меняет семантику окружения потребителя.
- Наличие `goga_tool_pybuggy` / `python-dotenv` в окружении pytest не проверяется — выяснится при
  запуске тестов.
- После `da5603d` automate-пайплайн не создаёт conftest вовсе; единственный создатель — `pybuggy init`.

## Приложение: ADR из discover (сохранён дословно)

# ADR: `pybuggy init` генерирует корневой `conftest.py` целевого проекта

Плагин pybuggy включается только явным вызовом `goga_tool_pybuggy.plugin.install()` из корневого
`conftest.py` — import-time auto-wiring нет, поэтому без этого файла тестовый набор не получает фикстуру
`api`. Раньше файл создавал скилл `pybuggy-api-automate-conftest` (stage `setup-conftest` automate-пайплайна),
удалённый коммитом `da5603d` — решено: обязанность создания `conftest.py` переносится в CLI-команду
`pybuggy init` (шаг в `run_init`, ячейка `commands/init`), чтобы инфраструктура запуска тестов появлялась тем же
командой, что инициализирует остальной goga-проект.

Status: accepted (2026-08-19, interview Q1–Q10).

## Решённые детали

- **Содержимое — фиксированный шаблон, дословно** (аналог жёсткой `_INSTALL_LINE` у Dockerfile-шага):

  ```python
  from dotenv import load_dotenv

  load_dotenv()

  from goga_tool_pybuggy import plugin

  plugin.install()
  ```

  `load_dotenv()` без аргументов уже означает `override=False` (CI/оператор может фиксировать окружение);
  порядок «`load_dotenv` до `install()`» сохранён — опции плагина резолвятся из `os.environ`.
- **Путь:** `<cwd>/conftest.py` — корень целевого проекта, где запускается pytest (`run_init` уже резолвит
  выходной корень как cwd).
- **Существующий файл:** перезапись только через `click.confirm` (default **no**); отказ → шаг пропускается с
  INFO-логом — зеркально пересозданию `.goga/config.yml` и tool-конфига в `run_init`.
- **Позиция шага:** последний в алгоритме `run_init` (после bootstrap usages). Ошибка записи → log + non-zero
  exit, как у остальных шагов. Наличие `goga_tool_pybuggy` / `python-dotenv` в окружении pytest не проверяется —
  выяснится при запуске тестов.
- **Размещение (DSL):** ячейка `commands/init` — чистая процедура `write_pybuggy_conftest(path: Path)`
  (всегда пишет, без TTY), проверка существования и confirm живут в `run_init` — тот же шов, что у
  `build_pybuggy_config` → `write_pybuggy_config`. Отдельная ячейка не заводится. CODEMANIFEST init-ячейки
  обновить (сигнатура + описание).
- **Документация:** только `plugin/.usages/enable.md` — дополнить указанием, что `pybuggy init` генерирует
  conftest автоматически (ручной путь остаётся для проектов без init). `skills/pybuggy/SKILL.md` не трогать.

## Considered Options

- **Слияние с существующим conftest** (маркер-проверка + дописывание pybuggy-блока в конец с сохранением
  пользовательского кода — инвариант удалённого скилла). **Отклонено** в пользу простого confirm/overwrite:
  механика merge в CLI избыточна; при отказе от перезаписи пользователь объединяет код вручную.
- **Разместить процедуру в ячейке `plugin`** или отдельной ячейкой. **Отклонено:** plugin-ячейка — про runtime
  pytest, а генерация файлов проекта — bootstrap-зона ответственности `commands/init` («одна зона
  ответственности — одна ячейка»).
- **Вернуть секцию «Инфраструктура» в `skills/pybuggy/SKILL.md`** с указанием на CLI. **Отклонено** —
  достаточно usage-документации.

## Consequences

- Существующий кастомный `conftest.py` никогда не мержится и не перезаписывается молча: либо подтверждённая
  замена, либо пропуск. Это сознательное отступление от инварианта старого скилла — «починить» его в будущем
  не надо.
- После `da5603d` automate-пайплайн больше не создаёт conftest вовсе; единственный создатель — `pybuggy init`.
- Шаблон жёстко фиксирован в коде init и не параметризуется (как версия `0.1.x` в Dockerfile-строке).
