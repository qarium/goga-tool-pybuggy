# Интерактивное построение `.goga/tools/pybuggy/config.yml` в команде `init`

## Current State

Файл `.goga/tools/pybuggy/config.yml` сегодня читается двумя ячейками, но **никем не создаётся**:

- **ячейка `config`** — `load_config()` (pydantic-модель `Config`) валидирует секцию `specs`: отображение «имя спеки → `SpecEntry`», где `SpecEntry = type (swagger|openapi), location, git?`, а `GitEntry = url, location, ref?`. Используется командами `generate`, `info`, `list`, `pull`.
- **ячейка `plugin`** — `ApiPlugin` (через pluginator) читает конфигурируемые через конфиг опции, описанные в `PluginConfigKeys`: `base_url`, `headers`, `timeout`, `data_key`, `error_key`, `retries`, `loader` (packages/modules), `assert_timeout`, `assert_delay`, `assert_field_class`, `assert_response_class`.

Команда `init` (`goga_tool_pybuggy/commands/init`) сейчас инициализирует goga-проект, копирует `.usages` ячейки `api` в `.goga/usages/cooks/pybuggy/` и регистрирует их в `.goga/config.yml`. Файл `config.yml` инструмента pybuggy она **не создаёт** — это явно зафиксировано в её контракте как ограничение («НЕ трогает `.goga/tools/pybuggy/config.yml`, не использует config-ячейку»).

## Description

Доработать команду `init`, добавив **интерактивное построение** файла `<cwd>/.goga/tools/pybuggy/config.yml`. Опрос запускается на каждом вызове `init`. Если файл уже существует — перед затиранием запрашивается подтверждение **(y/N)**; при отказе шаг генерации пропускается (существующий файл сохраняется), остальной `init` продолжается.

Источник схемы для опроса — два места:

1. **`PluginConfigKeys`** (ячейка `plugin`):
   - скалярные ключи (`base_url` [обязательный], `timeout`, `data_key`, `error_key`, `retries`, `assert_timeout`, `assert_delay`, `assert_field_class`, `assert_response_class`) опрашиваются по одному;
   - обязательный `base_url` пропустить нельзя; необязательные можно пропустить;
   - сложные (`headers`-dict, `loader`-секция) **не опрашиваются** — пишутся закомментированным примером с описанием структуры в комментарии.
2. **`specs`** (ячейка `config`): опрашивается интерактивно — имя спеки, `type` (swagger|openapi), `location`, опционально `git` (`url`, `location`, `ref`); поддерживается добавление нескольких спек.

Пропущенные необязательные поля всё равно попадают в конфиг **закомментированными** (с пояснением, что туда вписывать); заполненные поля записываются активными значениями.

## Scope

**In scope:**

- Новый интерактивный шаг построения `config.yml` внутри `init`.
- Перезапись существующего `config.yml` с подтверждением (y/N).
- Дата-драйвенный источник ключей из `PluginConfigKeys` и моделей `specs` (`Config`/`SpecEntry`/`GitEntry`).
- Опрос скалярных опций по одной; закомментированные записи для пропущенных необязательных полей и для `headers`/`loader`.
- Интерактивный ввод `specs` (несколько спек, обязательные `type`/`location`, опциональный `git`).
- Обновление контракта ячейки `init` (`CODEMANIFEST`/`.usages`): новые импорты схем из `config` и `plugin`, снятие старого ограничения.
- Раскрытие `PluginConfigKeys` ячейкой `plugin` как импортируемого контрактного типа (объявление в её `CODEMANIFEST` + реэкспорт через фасад `__init__.py`) — сопутствующее изменение контракта `plugin`, необходимое для импорта в `init`; состав значений enum не меняется.
- Testable-seam для интерактива (отдельная тестируемая рутина, как у `run_goga_init`) и тесты нового поведения.

**Out of scope:**

- Изменение команд `generate`, `info`, `list`, `pull`.
- Изменение моделей `Config`/`SpecEntry`/`GitEntry`.
- Изменение опций `ApiPlugin` и набора `PluginConfigKeys`.
- Неинтерактивный/автоматический режим генерации конфига.

## Acceptance Criteria

- Команда `init` создаёт `<cwd>/.goga/tools/pybuggy/config.yml` на каждом вызове.
- При наличии существующего файла выводится подтверждение (y/N); отказ сохраняет файл и не прерывает `init`.
- `base_url` (обязательный) не может быть пропущен; остальные скалярные ключи `PluginConfigKeys` опрашиваются и могут быть пропущены.
- Пропущенные необязательные поля присутствуют в конфиге закомментированными, с поясняющим комментарием.
- `headers` и `loader` не опрашиваются и записаны закомментированными примерами с описанием структуры.
- Секция `specs` заполняется интерактивно (имя, `type`, `location`, опциональный `git`); поддерживается несколько спек; в каждой спеке `type`/`location` обязательны, `git` опционален.
- Сгенерированный (заполненный) конфиг проходит `load_config()` (валидация `Config`: наличие `specs`, обязательные поля `SpecEntry`).
- Набор опрашиваемых ключей плагина берётся из `PluginConfigKeys` (а не дублируется вручную).
- `CODEMANIFEST`/`.usages` ячейки `init` отражают новые импорты из `config` и `plugin` и снятое ограничение на запись `config.yml`.
- Интерактив изолирован в тестируемой рутине; тесты покрывают создание, перезапись с подтверждением, пропуск полей и закомментированные записи.

## Stack

- **Frameworks:** click (CLI-фреймворк; интерактивные промпты и подтверждение, обёртка команды, маппинг ошибок в `click.ClickException`).
- **Libraries:** ruamel.yaml (запись `config.yml` с активными и закомментированными записями); `PluginConfigKeys` из ячейки `plugin` и `Config`/`SpecEntry`/`GitEntry` из ячейки `config` — как источник схемы.
- **Infrastructure:** нет.

## Risks and Constraints

- **Перезапись деструктивна:** повторный `init` перегенерирует конфиг. Смягчается подтверждением (y/N) перед затиранием существующего файла.
- **Эмиссия закомментированных строк/блоков** в ruamel.yaml (`# key:` и многострочные `headers`/`loader`/`git`) требует аккуратного рендеринга; существующий usage `ruamel-yaml` этот паттерн не описывает — запланировать дополнение.
- **Синхронизация шаблона с эволюцией схемы:** ключи берутся из `PluginConfigKeys`, а структура `specs` — из моделей ячейки `config`; это снижает дублирование, но ячейка `init` получает новые связи на `plugin` и `config`.
- **`base_url`** — обязательный и является Jinja2-шаблоном (рендерится в плагине); комментарий в конфиге должен это отражать.
- **Совместимость с `load_config()`:** генерируемый конфиг должен оставаться валидным для pydantic-модели `Config` (дополнительные ключи плагина игнорируются, `specs` обязателен).
- **Интерактив:** новый шаг — TTY-промпты; для тестирования требуется testable-seam (как у `run_goga_init`).

## Scope Estimate

Единая задача. Затрагивает ячейку `init` (код + контракт `CODEMANIFEST`/`.usages`) и её тесты; интерактив вынесен в тестируемую рутину. Декомпозиция не требуется.

## Existing Architecture

- Ячейка `init` (`commands/init`) — точка изменения; сегодня пишет в `.goga/config.yml` (регистрация usages), не в `.goga/tools/pybuggy/config.yml`.
- Ячейка `config` (`config/`) — источник схемы `Config`/`SpecEntry`/`GitEntry` для секции `specs`; новый импорт в `init`.
- Ячейка `plugin` (`plugin/`) — источник `PluginConfigKeys` для перечня опрашиваемых опций; новый импорт в `init`. **Важно:** на сегодня `PluginConfigKeys` не объявлена как контрактный тип в `CODEMANIFEST` ячейки `plugin` (упоминается только в аннотациях `ApiPlugin`) и не реэкспортируется фасадом `plugin/__init__.py` (`__all__ = ["ApiPlugin", "install"]`). Для корректного импорта `PluginConfigKeys` как типа (`Imports.Types` из `plugin`) с соблюдением границ ячеек ячейке `plugin` требуется раскрыть этот тип: объявить его контрактом в своём `CODEMANIFEST` и реэкспортировать через фасад (состав значений enum при этом не меняется — это не нарушает Out-of-scope «изменение набора `PluginConfigKeys`»).
- Ячейка `config` и ячейка `plugin` оба читают `.goga/tools/pybuggy/config.yml` — генерируемый файл должен оставаться совместимым с обоими потребителями.
