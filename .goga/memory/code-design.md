# Project rules

## Explicit ownership of behavior-breaking changes

When a redesign silently changes product behavior — most notably an optional-component decline that ends in an error exit while leaving partially initialized state that the re-entry guard then refuses — this branch must be owned as a deliberate, documented design decision: recorded in the design's environment and edge-case sections, presented as a normal outcome in usage documentation, noted in migration notes when it diverges from the previous major version, and covered by a negative test variant; it must never be left implicit or softened into a warning that defers the breakage to a later, mysterious failure. The classification runs in both directions: a defect fix that alters observable behavior for identical inputs — previously generated file paths, same-arguments behavior, or generated artifact content — is a formally breaking change regardless of corrective intent, so the verdict must be detected during investigation and work halted there, before planning, with the change escalated to the user in a dedicated report giving a concrete account of what breaks together with the minimal proposed fix; implementation proceeds only after the user's explicit override of the stop, and that override is recorded in the compatibility report and the final change report. Rollout of such a change is staged so existing consumers retain their prior output until the next regeneration repairs it in place, while fresh generations receive the new form immediately.

## Explicit scope governance

Approval covers only what was clearly confirmed and explicitly approved, and the approved defect description or plan defines the work: a lone failing standard gate never substitutes for a defect report, single-item emphasis in an approval reply is treated as a mandate for that item alone and resolved with one short, option-scoped follow-up question before implementation, and the landed change must match the approved plan exactly. Once the scope is approved, remediation is complete and single-pass: when every review finding is fixable within the design artifact itself and no governing contract is violated, all findings — including minor test-gap findings — are applied in one pass, the affected chains are then re-verified against the live stack, nothing is deferred or recorded as skipped, and the contracts stay unchanged; edits remain confined to the explicitly approved minimal set of spec-level value edits, leaving keys, annotations, signatures, footers, and runtime code untouched, with confirmation through the project's standard validation gates plus the full regression suite rather than by widening the change. When a proposed remedy is rejected as too aggressive, the rework removes only the confirmed defect and preserves the legitimate interactions entangled with it — collapsing a flawed prompt into total silent automation with zero remaining questions is over-correction, not a fix. Once scope is settled, unrelated pre-existing failures and discovered drift outside it are left untouched and flagged as recommended follow-ups in the final report rather than silently absorbed into the change.

## Documentation grounded in code and observed behavior

Factual statements in design documents must match the code they describe: dependency lists must exclude modules the code never calls, exception-handling claims must reflect the actual catch tuples and exception inheritance, and module layouts must include every constant the code reads; a consistency fix must remain purely textual and never smuggle in a behavioral change. Measurable statements in a design and its tests — counts, uniqueness, enumerations — are taken from the observed behavior of the real mechanism rather than from assumption, so an implementer verifying them never meets a false discrepancy. Whenever behavior changes in a cell, every surface that mirrors it moves in one lockstep change — the manifest contract, the implementation, the cell-level usage files, the documentation mirrors, and the tests that pin the behavior (pin-tests and literal expectations) — with the corrected value applied to all mirrored surfaces at once so that code, contracts, documentation, and tests never diverge from each other, while signatures, exit codes, written configuration shapes, session seams, and deliveries neutral to the change remain unchanged. Because stale fragments of old behavior hide in unexpected documents, a repository-wide text search for strings naming the old behavior is mandatory afterward, and the lockstep change must finish green through the lint and style gates; reviewing only the touched files is insufficient. Hand-authored usage guides are not derived from manifests, and sibling sections of a design drift when an edit changes its scope: a narrowly-worded acceptance criterion can pass while prose still describes a retired flow in retired vocabulary with stale counts, so review must compare every descriptive artifact against the current flow, extend the change past the literal criterion, and re-sync related sections after each applied edit.

## Honest and normatively complete specifications

Contract declarations, usage documentation, and specifications describe only what the engine actually consumes and enforces: declarations that can never execute are dropped, signatures are narrowed to live parameters, the real enforcement point is named when the engine silently discards a declared value, and flows that bypass the tooling entirely document the gap, so no reader is promised a delivery that never happens. Fixed per-category sets, deviations from uniform payload or behavior rules, and author-facing constraints implied by runtime mechanics (initialization that re-executes after every reset must be written idempotently) are recorded as explicit rules and exceptions in the specification itself — never as uniform claims contradicted in practice, undocumented exceptions, or implications buried in a single example.

## Privilege-scoped install sections in generated Dockerfiles

Install steps that require elevated rights — package installs into the image, OS-level dependencies — are emitted only inside an explicit root-privilege section of the generated Dockerfile: the section switches to the privileged user before those steps run and restores the unprivileged default user afterward. Appending privileged steps after the return to the default user produces a build that fails, so the generator must place all privileged work inside that guarded section and keep everything else under the default user.

## Single source of truth for version pins

Tool version constraints live in exactly one configuration record: generated install commands carry no explicit version flag of their own, and any code path that re-derives a version from installed package metadata is redundant and removed. No parallel pin may exist anywhere else, so no second copy can drift from the configuration record.

## Real-surface validation of externally-resolved references

Identifiers a package hands to an external platform for resolution — hook anchors, status anchor names, registry keys — are never guarded by literal-call assertions alone: a test that only replays the literal calls proves the string was sent, not that the platform can resolve it, so a reference naming a value the platform has never carried ships green and fails only as runtime skip-warnings. Such registrations carry at least one regression test that drives them through the platform's own resolution surface — the real registry resolved over the real built-in axis — so any dead reference fails the build, plus an end-to-end assembly check that expects zero warnings; the expected full assembled result is asserted from observed platform behavior, not from a hand-counted figure. The failure mode this guards against is silent and cascading: a registration anchored to a name absent from the platform's built-in status axis is skipped at runtime with only a warning rather than a hard error, and the skip cascades to every status chained below the dead anchor — so repeated skip warnings on every pipeline run signal a real defect, statuses silently missing from the assembled scale, not log noise.

## Selection-scoped delivery and the scripted-TTY trap

When one onboarding answer selects a variant (the api/web test kind), every artifact of that variant — surveyed questions, delivered usage files, config registrations — is gated on the variant's own durable signal (the engine-written tool config file), never delivered unconditionally: a variant's usages and registrations never cross into another variant's project, while genuinely variant-neutral artifacts (the sandbox subtree, the conventions slot) stay unconditional; artifacts skipped for a non-selected variant are logged at a low level rather than silently dropped, and previously initialized projects are left untouched. The same change pins a testing rule: a scripted-TTY double that answers an unscripted required prompt with its empty default sends the required-field re-ask into an infinite loop that presents as a silent OOM kill of the test run, not a test failure — so every required prompt's exact text must be scripted (or the double must answer non-empty), and any prompt-text change is propagated to every scripted map in the same change.

## Confirm-gated imperative interaction flows

Within the project's init command, artifacts that are structural invariants of the bootstrap are never surfaced as yes/no gates, since declining could only guarantee a later failure; the flow asks only for values that are genuinely configurable — such as the base image version and the build image name — and the artifact is always produced from those answers. Scope-wide confirmations, such as the autonomy flag, are asked only after the specification survey has fully completed, meaning after the first entry plus the entire "add another entry?" cycle; asking them inside the cycle because of declaration order is the defect being corrected, and the resulting configuration key and its contract stay unchanged. Fixed fields stay as declarative survey records, while any confirm-gated, branched, or repeated prompting — inexpressible in the engine's flat, one-level question model — is implemented as imperative code invoked from the amendment-time participation hook, with its results fed into the config payload; encoding such flows as static question trees is rejected because they flatten into plain sequential records. When such a flow collects repeating multi-field records, each record is gated behind a confirm prompt, then every field is asked individually in the same order as the primary record (required fields re-asked until valid, trailing optional fields skippable), looping back to the gate until declined; compressing repeated records into a single hand-typed delimited line is rejected. Executable validation steps that exercise these flows in design documents must pin the exact scripted answer map — which prompts lack a default and require an explicit value, which confirmations default to declining, and which gates must be declined to keep the run offline and deterministic — because a vague "accept the defaults" instruction silently depends on the environment.

## Full-grammar validation before side effects

The complete accepted syntax of declarative values is enforced at load time — not a subset of it — so malformed input aborts the run before the first external side effect (such as starting a service). Strict runtime checks remain only as defense in depth, never as the primary guard. Diagnostics must stand on their own: they name the offending key, value, and location, and every user-facing validation or expiry message renders the value that actually drives the underlying logic (no unbound or ambiguous inputs), keeps sub-second magnitudes legible instead of rounding them away, is free of duplicated wording, and names the default that caused a constraint failure so the corrective action is implied.

## Exclusive ownership of registration and output slots

Every shared namespace has exactly one owner, established before anything is written: framework markers and hooks are registered in a lifecycle phase that both precedes their first use and cannot be overwritten by other parties injecting hooks into the same namespace, with the injection order of those parties established before the phase is chosen. Likewise, each generated output slot has exactly one writer — when the generic engine writer would fill a slot first and thereby defeat a component's skip-if-exists gate, the session declares that slot skipped so the engine never writes it and the owning component's packaged asset lands instead. Relying on a gate to win a double-writer race, or on registration surviving a clobber, is rejected.

## Real-environment and legal-boundary test coverage

An adapter that manages external services carries at least one integration test against a real environment (gated on its availability), exercising the full lifecycle — startup, readiness by port and by health endpoint, liveness, log retrieval, idempotent shutdown — in addition to fake-based unit paths. Boundary constraints get the same edge treatment: when a constraint permits equality at its boundary, parameterizing only invalid values leaves that boundary unguarded, so a positive case at the legal equality point is required — otherwise a comparator regression can silently reject valid documents while the whole suite stays green.

## Migration and rename reference reconciliation

When the canonical configuration document changes its location or key vocabulary, the design must carry a complete rework inventory of every artifact that mechanically references it — test suites, shared fixtures, supporting code — and the implementing change must update all of them at once; an artifact omitted from the inventory falls outside plan scope and only fails after implementation. The same reconciliation applies at smaller scale: renaming a usage group or dependency in the project config physically relocates the synced usage files but never rewrites the manifest references to them, so the manifest path entries must always be updated by hand after such a rename.

## Onboarding questions matched to their value domain

Every value collected during onboarding is asked in the form its value domain dictates. A value whose valid set is defined by a downstream runtime is collected as a choice question mirroring that exact set, with a safe default, so invalid values are rejected at the prompt instead of surfacing only at a later execution stage — free-texting such a value is rejected. Open-ended configuration fields are the complement: they remain required free text, never gaining hard-coded provider defaults or being collapsed into one shared value, and each such prompt states why the information is needed so a user scoped to a single flow can still answer it.

## Authoritative signatures over schematic forms

Declared signatures and construction conventions bind every piece of code, tests included: objects are built exactly per the defined surface, constraints are honored, and fields that are not constructor parameters are assigned after construction rather than passed in. Pseudocode and scenario shorthand in design documents are schematic and never override the declared surface. Paired constraints extend to every configuration and test setup: where a validator constrains two timing fields against each other and one carries an incompatible default, any setup declaring a sub-second value on the constrained field must also declare an explicit compliant value for the other — otherwise validation fires at construction time and the behavior the setup exists to exercise is never reached.
