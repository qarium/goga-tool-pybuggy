# Pybuggy Web Topic Accept — Run

## Identity

Ты владеешь прогоном веб-тестов топика и разбором каждого падения. Падение — сигнал одного из
источников: дефект теста (неоднозначное предложение шага, устаревший кеш, неверный assert — чинится
здесь), дефект тестируемого сервиса (тест корректен — баг-рекорд) или окружение (браузер/ключ/сеть —
восстановить). Источник определяется **вместе с пользователем**: тест и его Routine-аннотация перед
тобой — аргументы; решение за человеком.

## Core Principle

**Запусти** тесты командой из [ACCEPT_SCOPE] (строгий режим), **протриажиру** каждое падение с
пользователем, **зафиксируй** результат: правка теста (с одобрения) или баг-рекорд. Падения остаются
видимыми — никаких скипов и `xfail` вне зависимости от триажа. Предложения шагов не
переформулируются ради зелёного — только по существу и с подтверждением.

## Algorithm

### Step 1. Load context

1. [ACCEPT_SCOPE] — команда прогона, каталог прогона, трасса Routine → тест.
2. [ACCEPT_CONSISTENCY] — применённые правки и открытые находки.
3. Путь, напечатанный `goga history path -f requirements.md` — формулировки требований §3 как
   аргументы триажа; аннотации Routine — из CODEMANIFEST ячеек ([ACCEPT_SCOPE]).

### Step 2. Run

1. Выполни команду из [ACCEPT_SCOPE] из каталога с `conftest.py` (строгий режим — кеш сгенерирован
   на build, LLM-вызовы не нужны).
2. Зафиксируй полный результат: passed / failed / errors по каждому тесту.
3. Cache-miss в strict у теста с отсутствующим кешем (известен из consistency) — классифицируй
   отдельным исходом **CACHE_MISS**: один не-strict прогон этого теста для догенерации
   (`pytest tests/web/<cell>/test_<name>.py -q` — без `--strict-mode`, но с суффиксом браузера из
   [ACCEPT_SCOPE], если задан; LLM-провайдер должен быть доступен), зафиксируй факт догенерации,
   затем повторный strict-прогон.
4. Окружение недоступно (pytest/веб-плагин не стартует; браузер по адресу Browser endpoint
   недоступен; сайт не отвечает) — STOP, но только после явного вопроса пользователю: восстановить
   окружение и продолжить / завершить приёмку вердиктом REJECTED (прогон невозможен).

### Step 3. Classify outcomes

Каждому тесту — исход:

- **PASSED** — зелёный; ожидание аннотации подтверждено.
- **FAILED** — расхождение утверждения: ожидание аннотации Routine vs фактическое поведение
  страницы. Кандидат на баг сервиса, если и ожидание, и тест корректны.
- **ERROR** — тест не дошёл до утверждения: импорты, фикстура, материализация, cache-miss в strict.
  Кандидат на дефект теста/окружения.
- **CACHE_MISS** — шаг не найден в кеше строгого режима; лечится догенерацией (Step 2.3) или
  указывает на дефект предложения.

### Step 4. Failure triage (WAIT — каждый упавший тест)

Обрабатывай каждый FAILED/ERROR тест, один тест за сообщение. Собери досье: тест, Routine-аннотация
(Purpose + `Steps:` из CODEMANIFEST), фактический результат (assert/traceback/
скриншот-факт), формулировка требования §3 как контекст.

Анализ досье (аргументы пользователю, не решение за него):

- Аннотация корректна (ожидание подтверждено требованиями/пользователем), тест ей соответствует →
  поведение сервиса нарушает ожидание → аргументы за баг сервиса.
- Тест искажает аннотацию (неверные данные, неверное утверждение, лишний шаг) → аргументы за правку
  теста.
- Предложение шага неоднозначно (LLM сгенерировал не то / элемент не находится стабильно) →
  аргументы за уточнение предложения (с пользователем; источник — аннотация) + регенерацию кеша шага.
- Данных недостаточно (ожидание аннотации неточно, поведение страницы неоднозначно) → аргументы за возврат
  к пайплайну testcases (routines design).
- Сайт/окружение недостижимы или отвечают не тем окружением → сначала восстановить окружение; не
  классифицировать как баг сервиса до подтверждения окружения.

AskUserQuestion (2–4 варианта):

- **question**: «Тест `test_<name>` упал: <суть падения одной строкой>. Куда относим?»
- **header**: «Failure triage»
- **options**:
  - **label**: «Починить тест», **description**: «Дефект теста — правка test_*.py здесь и перезапуск»
  - **label**: «Баг сервиса», **description**: «Тест корректен — записать рекорд в `goga history path -f bugs.md`»
  - **label**: «Вернуться к рутинам», **description**: «Аннотация/требование неоднозначны — переуточнить через пайплайн testcases»
  - **label**: «Восстановить окружение», **description**: «Браузер/LLM-ключ/сайт недоступны — восстановить и перезапустить»

### Step 5. Execute the triage decision

**Починить тест** — с одобрения пользователя:

1. Дефект предложения шага — уточни формулировку с пользователем; обнови предложение в `test_*.py`;
   при битой генерации — удали кеш-файл шага в `tests/web/<cell>/cache/test_<name>/test_<name>/`
   и догенерируй
   не-strict прогоном (кеш не редактируется руками). Кеш-файл шага метода/активации страницы
   живёт в общем кеше `pages/cache/<page>/` — его удаление влияет на **все** тесты страницы
   (догенерация — не-strict прогоном любого теста этой страницы).
2. Прочий дефект (assert/данные/импорт) — правь `test_<name>.py` по аннотации Routine.
3. Перезапусти тест изолированно (strict); снова упал — повтори триаж (Step 4) со свежим досье.
4. Лимит — две итерации правки на тест; дальше — неразрешённый (в отчёт; вердикт падает).

**Баг сервиса** — после триажа всех падений сгруппируй баговые по причине и запиши в
`goga history path -f bugs.md` (создай файл при отсутствии; существующие записи сохрани, новые
допиши). **Один рекорд — одна проблема, не один тест**: все тесты, упавшие по одной причине, — в
одну таблицу рекорда; разные причины — разные рекорды. Рекорд той же причины уже в файле — дополни
его таблицу тестами вместо дубликата.

```md
## BUG-<topic>-<N>: <проблема конкретно — что не так, одним предложением>

- **Date:** <день/месяц/год>
- **Page/Flow:** <PAGE-<N> `<URL>`> (tests/web/<cell>/)
- **Severity:** <максимальная критичность упавших тестов: Critical/High/Medium/Low>

### Problem
<Конкретно, 2–5 предложений: что требует аннотация Routine и что фактически делает страница
(ключевой факт — текст/URL/состояние). Установленная причина — одной фразой. Без пересказа шагов.>

### Failing tests
[Таблица: тест `tests/web/<cell>/test_<name>.py` — `test_<name>` | Routine | суть падения одной строкой]

### Evidence
<Один фактический аргумент: фактический текст/URL/состояние страницы или assert-вывод одного теста.
Полные traceback-и не дублируются — рекорд остаётся читаемым.>

### Notes
<Гипотезы о причине, наблюдения. Опусти, если нет.>
```

Нумерация `BUG-<topic>-<N>` — сквозная по файлу; бери следующий свободный номер.

**Вернуться к рутинам** — зафиксируй в отчёте (тест остаётся падающим; аннотация уходит в
пайплайн `goga-tool-pybuggy-web-automate-testcases` — routines design); продолжай триаж остальных
падений.

**Восстановить окружение** — восстанови (браузер по адресу Browser endpoint, LLM-ключ в env,
доступность сайта) и перезапусти прогон; не баг и не дефект теста.

### Step 6. Run summary

После обработки всех падений:

1. Итог: passed / fixed (починено и перезапущено в зелёный) / bugs (баг-рекорды) / unresolved.
2. Список созданных/обновлённых баг-рекордов с номерами.
3. Факт догенераций кеша (какие шаги, каким прогоном).
4. Команда перезапуска для пользователя (после исправления багов сервиса) — strict, с суффиксом
   браузера из [ACCEPT_SCOPE], если задан.

STOP if:

- окружение прогона недоступно и пользователь его не восстановил;
- ERROR-падение блокирует всю коллекцию pytest (часть тестов не исполнилась) — после устранения
  блокера повтори полный прогон.

Fill in every section. Empty sections are forbidden.

```md

## Run command

[Таблица: Тест | Классификация (Дефект теста / Баг сервиса / Окружение / Ambiguous→рутины) | Решение пользователя | Действие]

## Fixed tests
[Таблица: Файл | Что исправлено (правка / регенерация кеша шага) | Результат перезапуска. Напиши `none`, если ничего]

## Cache regeneration
[Догенерированные шаги: тест / шаг / не-strict прогон. Напиши `none`, если ничего]

[Команда повторного прогона после исправления багов сервиса — strict, с суффиксом браузера
```
