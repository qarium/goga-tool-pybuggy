# Pybuggy Web Cookbook

## Purpose

Принципы применения DSL `goga-cell` для проектирования **веб-тестовых** ячеек. Документ адаптирует
`goga-cookbook` и оставляет только релевантное веб-тестам: каждый тест — `Routine` с базовыми
`Usages`/`Annotations` из конфига проекта; шаги теста — предложения на естественном языке,
материализуемые через поверхность фикстуры-страницы (`page.step(...)`/`page.expect(...)`;
`web.step` — только у рутин без page-объекта).

Другие скиллы вызывают этот скилл, чтобы загрузить контекст проектирования веб-тест-ячеек.

## Behavior

Вызывающий скилл применяет эти принципы в своём контексте. Он не пересказывает `goga-cookbook`
целиком и не описывает внутренности других скилл — он принимает по этим принципам
проектные решения о веб-тест-ячейках.

# Принципы проектирования веб-тест-ячеек

## Context

Веб-тесты — отдельный проект, использующий pybuggy как фреймворк. Веб-тест-ячейка — каталог с
CODEMANIFEST внутри дерева тестов:

```
tests/web/<cell-name>/
└── CODEMANIFEST
```

Границы ячеек — дизайн-решение фазы cell-map: ячейка на страницу, объединение страниц одного
пользовательского флоу в одну ячейку или несколько ячеек на страницу — всё допустимо. Материализованные
тесты лежат рядом (`tests/web/<cell-name>/test_<name>.py`), кеш шагов — в
`tests/web/<cell-name>/cache/test_<name>/test_<name>/` (параметризованный кейс —
`…/test_<name>/test_<name>[<param_id>]/`), кеш предложений методов страниц — общий, в
`pages/cache/<page>/`.

## Test cell CODEMANIFEST

### Design order

1. **Header** — базовые `Usages` + `Annotations` (контракт работает в контексте базовых практик проекта).
2. **Body** — `Routine`: тест-кейс = Routine (отдельный кейс-слой не проектируется); одна Routine
   может покрывать несколько REQ через параметризацию; параметризация — решение фазы routines design.
3. **Footer** — `Author`, `CreatedAt`, `Description`.

### Header

**Базовый блок** `Usages` и `Annotations` берётся из `.goga/config.yml` (через `goga-codemanifest-base`)
и **идентичен для всех веб-тест-ячеек**:

- `Usages`: `conventions`, `pybuggy-web` (пути в `.goga/usages/`).
- `Annotations`: инструкции вида ``Use `pybuggy-web` for ...``.

Поверх базового блока ячейка может иметь **cell-specific usages** — см. раздел
"Cell-specific usages (tools)" ниже.

### Cell-specific usages (tools)

Веб-тест-ячейка, использующая инструмент подготовки данных, мок или утилиту, получает cell-specific
usage **поверх базового блока**:

```yaml
Usages:
  conventions: .goga/usages/conventions.md          # базовый блок — идентичен во всех ячейках
  pybuggy-web: .goga/usages/cooks/pybuggy/pybuggy-web.md
  faker: .goga/usages/cooks/faker.md                # cell-specific (только где используется)
```

- Ключ usage добавляется в Header **только когда файл существует** — `.goga/usages/cooks/<key>.md`
  должен быть на диске до начала проектирования ячейки.
- Подключение инструмента — две записи: строка `<key>: .goga/usages/cooks/<key>.md` в `Usages` +
  строка ``Use `<key>` for <подготовка данных/моки/утилиты>`` в `Annotations` затронутой ячейки.
  Бэктик-ссылка `` `<key>` `` резолвится сразу: ключ уже объявлен в `Usages` этой ячейки.
- Базовый блок остаётся **неизменным**. Cell-specific usage существует только в ячейках, использующих
  инструмент — его наличие в одних ячейках и отсутствие в других **не** является расхождением.
- REQ-покрытие и гранулярность Routine остаются **незатронутыми** (usage-инструменты принадлежат
  Header/Annotations, не Routine).
- Типичный веб-инструмент — usage-файл «тестовые креденшалы / как логиниться» (механизм входа и
  источник креденшалов, **без значений секретов**) или библиотека подготовки данных через API.
- Usage-файл страницы `page-<name>` — API page-объекта (фикстура `page_<name>`, методы): создаётся
  стадией pages testcases-пайплайна, когда повторяющаяся **без параметров** последовательность
  шагов рутин (предложения идентичны дословно, без маркеров `{% var %}` / `{{ … }}`) выносится
  в метод page-объекта; затронутая рутина сворачивает последовательность в одно
  предложение-цель и ссылается на метод: ``Use `page-login` for закрытие баннера cookie —
  метод `dismiss_cookie_banner`` ` — подключение в Header ячейки стандартное (ключ + строка
  ``Use `<key>` for …``).

### Body — Routine

Веб-тест — это `Routine` (без `methods`/`properties`); тест-кейс = Routine; одна Routine может
покрывать несколько REQ через параметризацию:

```yaml
"test_<name>(page_<name>)":
  location: test_<name>.py
  annotations: |
    ...
```

- Сигнатура: `test_<name>(<фикстуры>)` — без выхода (тест ничего не возвращает); параметры —
  **фикстуры-страницы** `page_<name>` (одна — `test_<name>(page_drivers_list)`; несколько —
  `test_<name>(entry_page, page_drivers_list)`: сначала страницы предусловий (вход), затем
  целевые). `web` (PrettyPlay) — только у рутин без page-объекта (внешние/литеральные страницы,
  прямой рантайм); фикстура страницы сама зависит от `web`. В материализованном тесте допустимо
  `def test_<name>(page_drivers_list):` без аннотации типа — pytest резолвит фикстуры по именам;
  аннотация типа — контракт CODEMANIFEST.
- Именование `snake_case`, `location: test_<name>.py` (правила `goga-cell-python`).
- Параметризация: когда одна Routine покрывает несколько REQ/вариантов, они перечисляются в аннотации —
  в `Data:` и/или `Steps`; CODEMANIFEST не описывает механизм параметризации (например,
  `@pytest.mark.parametrize`) — он возникает при генерации тестового кода из Routine. Одна Routine
  соответствует одному `test_<name>.py` (несколько кейсов → один файл).
- Критерий параметризации — линейность: объединяются в одну Routine только REQ-варианты с совпадающим
  набором шагов и проверок — варианты различаются значениями (заполняемые данные, ожидаемые тексты),
  но не тем, какие шаги и проверки выполняются. Другой набор шагов или проверок — отдельная Routine:
  тест, материализованный из параметризованной Routine, линеен, поэтому логические конструкции в теле
  теста (`if`/`else` и подобные) свидетельствуют об избыточной параметризации.

### Footer

- `Author` — всегда `Goga`.
- `CreatedAt` — день/месяц/год.
- `Description` — зачем существует ячейка (какие страницы/флоу/топик она тестирует).

## Routine annotation standard

Аннотация Routine должна быть достаточной для реализации без уточнений. Веб-тесты используют
**строгую структуру** упорядоченных секций. Порядок фиксирован:
**Purpose → `Precondition:` → `Data:` → `Prompt:` → `Steps:` → `Use …`**.

Секции **разделены пустой строкой**: пустая строка следует после Purpose и перед каждой из
`Precondition:` / `Data:` / `Prompt:` / `Steps:` / `Use …`. Две соседние секции без пустой строки
между ними нарушают структуру.

**1. Purpose — без ярлыка.** Секция утверждает, что и зачем Routine проверяет — поведенческое
утверждение требования своими словами. Это первый абзац аннотации.

**2. `Precondition:` — фикстуры и предусловия.** Маркированный список (`- `): буллет **каждой
фикстуры сигнатуры** — фикстура-страница `` `page_<name>` `` (модуль `pages/<…>_page.py`, path,
назначение; веб-рантайм активируется документом `.goga/tools/pybuggy/web.yml`) либо `` `web` ``
у рутин без page-объекта — плюс общие предусловия (авторизация — поведенчески, например
«выполнен вход как тестовый пользователь `<роль>`»; состояние системы/данные ДО теста по кейсу).
Имя фикстуры обязано нести бэктик.

**3. `Data:` — данные, создаваемые внутри теста.** Маркированный список внутренних данных теста:
переменные, ключи, захваты значений со страницы (захват — маркер `{% var <имя> %}` внутри
предложения шага; ссылка на захваченное значение — `{{ <имя> }}` в последующих предложениях),
не привязанные к одному шагу. Конкретные значения шагов остаются внутри `Steps`. Секция опускается,
когда таких данных нет.

**4. `Prompt:` — пер-тестовые доп-инструкции генерации.** Маркированный список (`- `) особенностей
страницы, мешающих генерации шага (баннер cookie поверх страницы, нативный `<select>` вместо
кастомного дропдауна, формат дат DD.MM.YYYY) — только факты из требований (§2 страницы). Это
только странности страницы, **не адресация элементов**: локаторы, селекторы и testid (CSS, XPath,
data-атрибуты) в `Prompt:` — как и в любой другой секции аннотации — запрещены; адресат действия
называется видимым именем в самом предложении шага (видимые имена — стабильный пользовательский
контракт страницы, локаторы связывают аннотацию с разметкой). Каждый
буллет материализуется декоратором `@generation_prompt("<текст>")` над тестом — импорт
`from goga_tool_pybuggy import generation_prompt`, порядок декораторов = порядок буллетов, тексты
дословны. Секция опускается, когда особенностей нет; секреты в буллетах запрещены (текст попадает
в промпт LLM-провайдера и в репозиторий).

**5. `Steps:` — нумерованные шаги теста.** Шаги приходят из тест-кейса (Действие / Данные / Ожидание).
Каждый пункт `Steps:` материализуется **ровно в одно предложение шага**:
действие → `page.step("<предложение>")`, проверка → `page.expect("<предложение>")`,
мини-сценарий из нескольких тесно связанных шагов → `with page.group("<достигаемое состояние>"):`
(через поверхность активированной страницы; `web.step`/`web.expect`/`web.group` — только рутинам
без page-объекта). Логика, не код —
шаги выражаются обыкновенным языком (одно действие на предложение, назван адресат и действие),
без pytest/playwright-кода. Нумерованный список (`1. `).

Правила предложений шагов (из `pybuggy-web`):
- один шаг = одно действие; в предложении названы цель и действие («Открыть `https://…`»,
  «Заполнить поле „Email“ значением …», «Нажать кнопку „Войти“»); адресат называется видимым
  именем/текстом — локаторы, селекторы и testid в предложениях запрещены;
- навигация на страницу тестируемого сайта выражается предложением с путём («Открыть страницу
  `/login`») и материализуется активацией фикстуры страницы `page_<name>()` — URL компонуется
  рантаймом из `site.base_url`; полный URL в предложении — только внешние страницы и
  query-адреса;
- группа (`page.group`) — мини-сценарий из 2–3 тесно связанных действий, которые **вместе меняют
  состояние страницы или виджета** (заполнить и отправить форму, выполнить вход, довести диалог
  до результата): предложение-группа называет достигаемое состояние, действия внутри поодиночке
  не значимы — лечение группы идёт рядом с раннего затронутого шага; независимые действия
  группами не объединяются;
- адрес страницы тестируемого сайта — путь относительно base_url (`/catalog`, как в §2
  требований); полный URL — только внешняя страница (чужой origin) и адрес вне сайта; смена
  окружения — смена `site.base_url` web.yml (+ один прогон без `--strict-mode`), предложения
  шагов не меняются;
- ожидания — отдельными `page.expect`-предложениями («На странице отображается текст …»,
  «URL стал `https://…/orders`»);
- захват значения со страницы — маркер `{% var <имя> %}` внутри предложения шага («Сохранить
  заголовок третьего видео в `{% var video_title %}`»); захваченное значение подставляется
  в последующие предложения — шаги и проверки — маркером `{{ <имя> }}` («Открыть видео
  `{{ video_title }}`»); захват уместен **только** для значений, неизвестных при написании
  теста (динамика страницы: заголовок N-го элемента, сгенерированный номер заказа) — статические
  значения (URL, вводимые и ожидаемые литералы) пишутся в предложения без маркеров;
- **секреты в предложениях запрещены** (всё попадает в промпт LLM-провайдера и в репозиторий):
  вход описывается поведенчески — «Выполнить вход как тестовый пользователь `<роль>`»;
  значения секретов берутся из env/usage-файла и в шаги не пишутся.

**6. `Use …` — только специфичные для Routine usages.** Секция закрывает аннотацию и перечисляет
usages, используемые **в этой Routine**, которых глобальные `Annotations` заголовка ещё не покрывают.
Базовые практики (`pybuggy-web`, `conventions`) уже связаны в `Annotations` заголовка CODEMANIFEST —
**не дублируйте** их в Routine. Сюда попадают только cell-specific инструментальные usages
(например, ``Use `faker` for генерация test_id``). Секция опускается, когда у Routine нет
специфичных usages. Бэктик-ссылки обязаны резолвиться в контексте CODEMANIFEST.

**Не используются** в тестах: `Requirements:`/`Constraints:` (их содержимое при необходимости
переезжает из кейса в `Precondition:`/`Data:`); `Algorithm:` заменяется на `Steps:`.

## Кеш шагов и режимы прогонов (важно для дизайна и приёмки)

- Кеш создаётся **первым прогоном** теста: LLM генерирует Playwright-код для каждого предложения и
  кладёт кеш-файлы в `tests/web/<cell>/cache/test_<name>/test_<name>/` (инлайн-шаги теста;
  параметризованный кейс — `…/test_<name>/test_<name>[<param_id>]/`; шаги методов
  page-объектов — в общем кеше страницы `pages/cache/<page>/`); кеш коммитится в репозиторий.
- Первый прогон обязан идти **без** `--strict-mode` (strict = 0 LLM-вызовов — новый шаг в strict
  падает). Повторные прогоны и CI — со `--strict-mode` (реплей из кеша).
- Кеш не редактируется руками; для регенерации шага его кеш-файл удаляется, и следующий не-strict
  прогон пересоздаёт его.
- Routine-аннотация — источник, из которого генерируется тест: маркер/декоратор или деталь,
  существующая только в коде, теряется при следующей регенерации из Routine — всё значимое
  выражается в аннотации.

Пример:

```yaml
"test_search_finds_results(page_catalog)":
  location: test_search_finds_results.py
  annotations: |
    Проверяет, что поиск на странице каталога находит товары по запросу и показывает результаты.

    Precondition:
    - `page_catalog`: фикстура-страница каталога (pages/catalog_page.py, path /catalog;
      веб-рантайм активируется документом .goga/tools/pybuggy/web.yml).
    - Каталог доступен без авторизации.

    Steps:
    1. Открыть страницу каталога /catalog.
    2. Заполнить поле поиска значением "ноутбук" и нажать кнопку «Найти».
    3. На странице результатов отображается хотя бы один товар с текстом "ноутбук".
    4. URL страницы результатов — /catalog?q=ноутбук.

    Use <usages> специфичные для Routine
```

Здесь шаги 1–2 материализуются как `page.step(...)` (шаг 1 — активацией
`with page_catalog() as page:`), шаги 3–4 — как `page.expect(...)`.
