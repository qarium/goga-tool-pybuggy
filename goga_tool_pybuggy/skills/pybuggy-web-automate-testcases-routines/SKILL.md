# Pybuggy Web Topic Testcases — Routines

## Identity

Ты проектируешь рутины топика — сразу целиком, без промежуточного слоя кейсов. Тест-кейс = Routine:
каждая рутина несёт шаги-предложения (будущие `page.step(...)`/`page.expect(...)` через
фикстуру-страницу).
Каждую рутину показываешь пользователю и ждёшь аппрув; при необходимости — правки.

## Core Principle

Рутина строится только из фактов [TESTCASES_INTAKE] (§2 страницы с итоговыми URL, §3 REQ, §4 auth и
предусловия, §6 интеграции) — элементы и поведение не выдумываются. Локаторы/селекторы/testid
(в том числе оставшиеся в контексте сессии из исследования страниц) в аннотации не попадают:
адресация элементов — видимыми именами в предложениях шагов. Параметризация — решение этой
фазы: варианты с совпадающим набором шагов и проверок (различаются только данными) — одна
параметризованная Routine; другой набор шагов или проверок — отдельные Routine.

## Algorithm

### Step 1. Load context

1. [TESTCASES_INTAKE] — requirements.md и базовый блок Header.
2. [TOOLS_REPORT] — доступные инструменты (ключи существующих usage-файлов).

### Step 2. Build the routine set

1. **Реестр покрытия**: каждый REQ §3 обязан быть покрыт хотя бы одной рутиной — фиксируется
   в таблице Coverage этого отчёта. Исключение REQ — только с решением пользователя.
2. **Main behavior** → рутины главных сценариев: стартовый адрес (путь относительно base_url —
   из §2), предсостояние (§4: авторизация — поведенчески), шаги-предложения по смыслу требования
   (одно действие на предложение), проверки — отдельными expect-предложениями. Рутина,
   стартующая на странице с page-объектом (§2 — привязка `page_<name>`), подключает его:
   ``Use `page-<name>` `` — навигационное предложение («Открыть страницу `/login`»)
   материализуется активацией `page_<name>()`, URL компонуется рантаймом из `site.base_url`.
3. **Error behavior** → негативные рутины — только при наличии error-REQ в §3 (негативное покрытие
   в UI-тестах — редкий кейс: подраздел пуст или осознанно исключён пользователем — негативных
   рутин не проектируй и не выдумывай): условие ошибки → ожидаемая реакция страницы (текст
   валидации / пустое состояние / 404).
4. **Параметризация по линейности**: одинаковые шаги/проверки, разные данные → одна Routine
   с вариантами в `Data:`; разный набор шагов/проверок → отдельные Routine.
5. **Имя и location**: `test_<snake_case>` от сути (`test_search_finds_results`); сигнатура —
   фикстуры-страницы рутины `test_<name>(page_<name>)` (несколько — `test_<name>(entry_page,
   page_<name>)`: сначала страницы предусловий/входа, затем целевые); `location: test_<name>.py`.
6. **Аннотация** — строгая структура (goga-cell / cookbook): Purpose (что и зачем проверяет
   рутина — поведенческое утверждение требования) → `Precondition:`
   (буллет каждой фикстуры сигнатуры: `` `page_<name>` `` — фикстура-страница с модулем и path;
   + предусловия) →
   `Data:` (захваты переменных и/или варианты параметризации; опускается, если пусто) →
   `Prompt:` (пер-тестовые доп-инструкции генерации — особенности страницы из §2, мешающие
   генерации: баннер cookie, нативный `<select>`, формат дат; только странности страницы, без
   адресации элементов — локаторы/селекторы/testid в `Prompt:` запрещены, адресат называется
   видимым именем в предложении шага; один буллет = один
   `@generation_prompt`-текст; опускается, если особенностей нет) → `Steps:`
   (нумерованные предложения) → `Use …` (ключи, используемые этой рутиной: инструменты из
   [TOOLS_REPORT] и `page-<name>` страниц рутины — фикстура/активация/методы; опускается,
   если нет ни тех, ни других). Пустая строка между секциями.
7. **Правила предложений шагов**: один шаг = одно действие (названы цель и действие); адресат —
   видимое имя/текст элемента (локаторы, селекторы, testid в предложениях запрещены — даже
   известные из исследования); адрес страницы тестируемого сайта — путь относительно base_url
   (`/catalog`, из §2), полный URL — только внешняя страница (чужой origin); секреты запрещены (вход — «Выполнить вход
   как тестовый пользователь `<роль>`», значения из env/usage-файла); каждая проверка — отдельное expect-предложение (
   исключение — транзитные тосты/баннеры, исчезающие сами через N секунд (тайминг из §2 деталей страниц):
   их подтверждение и чтение значения (захват `{% var %}`) живут в самом предложении-триггере
   — отдельное expect-предложение не успеет: код предложения генерируется LLM перед его
   исполнением, за LLM-раунд транзит исчезает, группа/метод page-объекта не спасают — единица
   генерации предложение); захват значения со страницы — маркер `{% var <имя> %}` внутри предложения шага («Сохранить
   заголовок третьего видео в `{% var video_title %}`»), ссылка на захваченное значение — маркер `{{ <имя> }}`
   в последующих предложениях, шагах и проверках («Открыть видео `{{ video_title }}`»);
   захват уместен только для значений, неизвестных при написании теста (динамика страницы) —
   статические значения (URL, вводимые и ожидаемые литералы) пишутся в предложения без
   маркеров; мини-сценарий из 2–3 тесно
   связанных шагов → одно предложение-группа (`page.group`). Критерий группы: набор действий
   **меняет состояние страницы или виджета** — заполнить и отправить форму, выполнить вход, довести
   многошаговый диалог до результата; предложение-группа называет достигаемое состояние, действия
   внутри группы поодиночке не значимы (упавший шаг лечится рядом с раннего затронутого — диагноз
   по всей группе). Независимые действия группами не объединяются.

### Step 3. WAIT — approval per routine

Каждая рутина — цикл «показ → решение», одна рутина за сообщение. Порядок внутри сообщения жёсткий:

1. **Сначала текст**: напечатай рутину целиком обычным текстом сообщения — имя, сигнатуру,
   `location`, полную аннотацию (все секции). Напечатанная рутина — то, что пользователь
   утверждает; AskUserQuestion без напечатанной перед ним рутины = утверждение вслепую =
   нарушение пайплайна.
2. **Затем вопрос**: AskUserQuestion (2–4 варианта) в том же сообщении, после текста рутины.
   Вопрос называет рутину по имени («Рутина `test_<name>` — утверждаем?»); содержимое рутины
   в вопрос и варианты не дублируется.
3. Никогда не вызывай AskUserQuestion раньше текста рутины и не прячь рутину в thinking,
   описание вопроса или варианты — она обязана быть видна пользователю в теле сообщения.

Варианты:

- «Утверждаю»;
- «Правка» — что изменить (применить, снова напечатать рутику целиком текстом и снова спросить);
- «Отклонить» — рутина не нужна (вернуться к реестру покрытия: REQ закрыть другой рутиной или
  исключить с решением пользователя).

### Step 4. Produce the [ROUTINES_REPORT]

STOP if:

- не удаётся спроектировать ни одной конкретной рутины (нет фактов о страницах);
- REQ-реестр невозможно покрыть и пользователь не подтверждает исключения;
- пользователь не утверждает рутину после итераций правок.

## Output Format

Fill in every section. Empty sections are forbidden.

```md
# [ROUTINES_REPORT]

## Routines

### test_<name> (location: test_<name>.py)

    "test_<name>(page_<name>)":
      location: test_<name>.py
      annotations: |
        [полная аннотация — Purpose, Precondition, Data, Prompt, Steps, Use]

**User Decision:** утверждено / правки: <что>

### test_<next_name> (location: test_<next_name>.py)

[…]

## Coverage

| REQ | Routine(s) |
|-----|------------|
| REQ-1 | test_… |

[Каждый REQ §3 покрыт (или явно исключён с решением пользователя). Реестр — сессионный:
REQ-идентификаторы в CODEMANIFEST не хранятся; проверку реестра против §3 выполняет фаза assembly.]

## Open Questions

[Что требует уточнения. Напиши `none`, если ничего.]
```
