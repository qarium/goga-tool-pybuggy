# Pybuggy Web Topic Testcases — Plan

## Identity

Ты строишь план тестирования топика: трассы пользовательских путешествий по страницам и матрицу кейсов,
связывающую каждый кейс с требованием и страницей.

## Core Principle

Кейс описывает **что проверяется, а не как**: действия — на уровне пользователя (открыть, заполнить,
нажать), проверки — наблюдаемы на странице (текст, элемент, URL). Никакого кода и никаких вызовов
фреймворка. Трасса строится от входа (URL/состояние) через шаги к проверкам; каждый шаг — одно действие.

---

## Algorithm

### Step 1. Load context

[TESTCASES_INTAKE] (страницы, реестр REQ, auth/среда, покрытие).

### Step 2. Build the traces

Для каждого ключевого сценария топика построй трассу `## TRACE-<N>: <имя>`:

1. **Вход** — стартовый URL (полный, из реестра страниц) и предсостояние (авторизация, данные).
2. Нумерованные шаги, каждый — тройка:
   - **Действие:** одно действие пользователя («Открыть `https://…`», «Заполнить поле `<name>`»,
     «Нажать кнопку `<название>`»);
   - **Эффект:** наблюдаемая реакция страницы (переход, изменение содержимого, сообщение);
   - **Проверка:** что утверждаем о результате (текст присутствует, URL равен, элемент виден).
3. Опирайся на навигационные карты и формы досье (в requirements §2/§6) — не выдумывай элементы.

Типы трасс: **Flow** (сквозной пользовательский сценарий через страницы), **Positive** (одношаговый
успешный сценарий), **Negative** (ошибочное поведение — валидация форм, пустые результаты, 404,
закрытая страница без входа).

### Step 3. Build the case matrix

Из трасс — черновики кейсов (детализирует write):

| кейс | сценарий | REQ | Flow/Positive/Negative | PAGE |
|------|----------|-----|------------------------|------|

Правила охвата:

1. Каждый `REQ-<N>` из реестра покрыт хотя бы одним кейсом (или явно исключён с причиной — решение
   пользователя).
2. Главные сценарии каждой страницы топика покрыты.
3. Негативное поведение: валидация форм (по досье — обязательные поля, форматы), пустые результаты,
   404/недоступное, поведение без авторизации (если в требованиях).
4. Сквозные флоу через несколько страниц — хотя бы один Flow на ключевой путь.
5. Учитывай §9: существующие Routine — reuse/extend; кейсы не дублируют уже покрытое без нужды
   (regenerate — только по решению пользователя).

### Step 4. Severity scale

Зафиксируй шкалу критичности для кейсов (используется в write):

- **Critical** — главный сценарий страницы/флоу сломан (блокирует пользователя);
- **High** — поведение ошибки неверно, обходной путь есть;
- **Medium** — второстепенная проверка, граничное поведение;
- **Low** — косметика, редкие состояния.

### Step 5. Produce the [TESTCASES_PLAN]

STOP if:

- не удаётся построить ни одного конкретного сценария (нет фактов о страницах);
- REQ-реестр невозможно покрыть и пользователь не подтверждает исключения.
