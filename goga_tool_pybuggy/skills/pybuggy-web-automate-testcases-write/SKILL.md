# Pybuggy Web Topic Testcases — Write

## Identity

Ты собираешь финальный артефакт кейсов из выводов предыдущих шагов и сохраняешь его в файл.

## Core Principle

Кейс описывает **что проверяется, а не как**: действия на уровне пользователя, проверки наблюдаемы
на странице, данные конкретны (кроме секретов — только источник). Никакого тестового кода и терминов
фреймворка (pytest/playwright/фикстуры). Один шаг = одно действие.

---

## Algorithm

1. Собери входы: [TESTCASES_INTAKE], [TESTCASES_PLAN], [TOOLS_REPORT].
2. Пронумеруй кейсы `TC-<N>` (последовательно, начиная с 1, без пропусков и дублей — в порядке
   групп плана).
3. Собери каждый кейс из черновика матрицы и его трассы: шаги трассы становятся шагами кейса,
   проверки трассы — ожиданиями шагов и итоговым результатом.
4. Concrete data: заполняй конкретные значения из досье (значения полей, тексты кнопок, URL) — не
   плейсхолдеры. Секрет — только ссылкой на источник («значение тестового пароля из env `<имя>`»).
5. Свяжи каждый кейс: поле `requirements` — `REQ-<N>` через запятую (все требования, которые кейс
   покрывает); поле `page` — `PAGE-<N>` стартовой страницы (для Flow — список).
6. Предусловия авторизации записывай поведенчески: «выполнен вход как тестовый пользователь `<роль>`»
   (+ `см. <key>` если заведён usage-файл креденшалов) — без значений.
7. Собери Requirements coverage matrix — строка на каждый REQ §3; источник истины — поля
   `requirements` кейсов (после сборки всех кейсов).
8. Добавь `## Total number of test cases: N`.
9. Сохрани [TOPIC_TESTCASES] по пути, напечатанному `goga history path -f testcases.md`
   (перезаписывай при повторных запусках).

STOP if:

- ни один полный кейс не построен (нет шагов с Действие/Данные/Expectation);
- матрица покрытия оставляет REQ непокрытыми без зафиксированного исключения.

---

## Output Format

Сохрани результат по пути, напечатанному `goga history path -f testcases.md`. Содержимое файла
следует формату ниже. Fill in every section. Empty sections are forbidden.

```md
### Detailed web test cases: [Topic name]

Каждый кейс несёт стабильный идентификатор `TC-<N>`; поле `requirements` связывает его с REQ-<N>
требований §3; поле `page` — со страницей PAGE-<N>. Источник истины матрицы покрытия — поля
`requirements` кейсов.

## <Сценарий 1>

### Flow

#### TC-1: <title>

- **Severity:** [Critical / High / Medium / Low]
- **Requirements:** REQ-1, REQ-2
- **Page:** PAGE-1

**Preconditions:**

- [Авторизация поведенчески: «выполнен вход как тестовый пользователь `<роль>`» — при необходимости;
  без авторизации — не указывается]
- [Данные/состояния: «в каталоге есть товар `<имя>`» / «данные готовятся библиотекой `<key>`»]

**Execution steps:**

1. **Действие:** Открыть `https://…` (полный URL страницы)
   **Данные:** —
   **Expectation:** страница открылась, заголовок `<текст>`
2. **Действие:** Заполнить поле `<name>` значением `<конкретное значение>`
   **Данные:** `<значение>`
   **Expectation:** значение отображается в поле
3. **Действие:** Нажать кнопку `<название>`
   **Данные:** —
   **Expectation:** `<наблюдаемая реакция: переход на URL … / текст … / элемент …>`

**Expected result:** [Измеримый итог кейса — что в сумме доказано]

#### TC-2: …

### Positive / Negative

[…]

## <Сценарий 2>

[…]

## Total number of test cases: N

## Requirements coverage matrix

| REQ | Covered by | Status |
|-----|------------|--------|
| REQ-1 | TC-1, TC-2 | covered |
| REQ-2 | — | not covered (исключение: <причина и решение пользователя>) |

Каждая строка — требование из §3 requirements.md. `covered` — есть кейс с этим REQ в поле
`requirements`; `not covered` допустим только с зафиксированным решением пользователя.
```
